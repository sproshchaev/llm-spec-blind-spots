# Спецификация интеграции интернет-магазина с WMS логистического партнёра

Oct 18, 2026 · Версия 0.1 (черновик)

## 1. Общие сведения

Интеграция связывает платформу интернет-магазина с WMS логистического партнёра через собственный интеграционный сервис: заказы уходят на склад, статусы отгрузки и остатки возвращаются в магазин. Цель — убрать ручной перенос заказов, показывать покупателю актуальный статус и трек-номер, не продавать товар, которого нет на складе.

**Участники**

| Система | Владелец | Роль в интеграции |
| --- | --- | --- |
| Платформа магазина (Shop) | Мы | Источник заказов и карточек товаров, потребитель статусов и остатков |
| Интеграционный сервис (Integration) | Мы | Очереди, маппинг, повторы, журнал обмена, сверки |
| WMS партнёра | Логистический партнёр | Приём заказов, резерв, сборка, отгрузка, учёт остатков |

**В объёме первой версии:** номенклатура, заказы (создание, изменение, отмена), статусы отгрузки, остатки, возвраты от покупателей.

**Вне объёма:** приёмка поставок от поставщиков, инвентаризации, биллинг услуг склада, B2B-отгрузки. Их можно добавить второй фазой на той же архитектуре.

**Термины**

| Термин | Значение |
| --- | --- |
| SKU | Артикул товара в магазине, единый ключ товара в обеих системах |
| Свободный остаток | Количество на складе минус резервы, брак и блокировки — то, что можно продать |
| Событие | Сообщение об изменении состояния (статус заказа, остаток) с уникальным `event_id` |
| Снапшот | Полная выгрузка остатков по всем SKU на момент времени |
| DLQ | Очередь сообщений, которые не удалось обработать после всех повторов |
| Идемпотентность | Повторная отправка того же сообщения не создаёт дубль и не меняет результат |

## 2. Допущения и ограничения

Спецификация написана до получения документации API партнёра, поэтому опирается на допущения ниже. Каждое нужно подтвердить (раздел 15); если допущение не подтвердится, меняется только адаптер WMS, а каноническая модель данных и логика магазина остаются прежними.

1. WMS предоставляет REST/JSON API для приёма заказов и товаров и умеет отправлять вебхуки о статусах и остатках. Если вебхуков нет — интеграционный сервис опрашивает WMS по расписанию (polling).
2. Склад один. Мультискладская схема потребует поля `warehouse_id` во всех сообщениях — оно заложено в модель заранее.
3. Партнёр сам передаёт посылки в службу доставки и возвращает трек-номер. Этикетки печатает склад.
4. Ключ товара в обеих системах — SKU магазина. Ключ заказа в WMS — номер заказа магазина (`order_number`).
5. На склад уходят только заказы, готовые к сборке: оплаченные онлайн или подтверждённые оператором (наложенный платёж).
6. Частичная отгрузка допустима: склад может отгрузить меньше заказанного при недостаче, магазин получает фактический состав.
7. Источник истины по физическим остаткам — WMS; по заказам и ценам — магазин.

## 3. Архитектура

Магазин и WMS не вызывают друг друга напрямую: между ними стоит наш интеграционный сервис, который изолирует магазин от формата и доступности API партнёра.

&#91;embedded content: архитектура интеграции · 3 системы, брокер, 2 направления\]

Команды магазина идут по левой колонке вниз, события склада — по правой вверх; при недоступности WMS сообщения ждут в брокере и уходят после восстановления.

**Почему отдельный сервис:** смена WMS или версии её API меняет только адаптер; повторы, журнал и сверки не нагружают платформу магазина; одна точка контроля всего обмена.

**Требования к технологиям** (выбор — за командой): брокер с доставкой at-least-once и порядком внутри партиции (Kafka, RabbitMQ или аналог); реляционная БД для outbox, журнала обмена и таблицы обработанных `event_id`; формат сообщений — JSON, время — ISO 8601 в UTC, суммы — decimal строкой или числом с двумя знаками.

## 4. Поток 1: номенклатура (Shop → WMS)

Товар должен существовать в WMS до первого заказа и до приёмки на склад, иначе WMS отклонит заказ. Магазин отправляет карточку при создании товара и при каждом изменении полей из таблицы ниже.

**Триггеры:** создание товара; изменение любого передаваемого поля; ручная переотправка из админки; ночная полная выгрузка активных SKU для сверки.

| Поле (канон) | Тип | Обяз. | Описание |
| --- | --- | --- | --- |
| `sku` | string(64) | да | Артикул, неизменяемый ключ |
| `name` | string(255) | да | Наименование для сборщика и документов |
| `barcodes` | string\[\] | да | Все штрихкоды (EAN-13, внутренние); хотя бы один |
| `weight_g` | int | да | Вес брутто в граммах |
| `length_mm`, `width_mm`, `height_mm` | int | да | Габариты упаковки |
| `unit` | enum | да | `pcs` (по умолчанию), `set`, `kg` |
| `is_active` | bool | да | `false` — товар выведен, новые заказы по нему не уходят |
| `requires_serial` | bool | нет | Учёт серийных номеров / кодов маркировки при сборке |
| `shelf_life_days` | int | нет | Срок годности, если товар учитывается по партиям |
| `fragile` | bool | нет | Признак хрупкости для упаковки |
| `image_url` | string | нет | Фото для сборщика |

**Правила:**

- Удаление товара в WMS не передаётся, только `is_active=false`.
- Изменение SKU запрещено; новый SKU = новый товар.
- Если WMS отклонил карточку (дубль штрихкода, нет габаритов), товар получает в магазине флаг «не синхронизирован со складом», и его заказы не уходят до исправления. Ошибка видна в админке и уходит в алерт.

## 5. Поток 2: заказы (Shop → WMS)

Заказ уходит на склад автоматически, как только становится готов к сборке; до ответа WMS он считается «передаётся на склад» и не может быть передан повторно другим путём.

**Триггер отправки:** переход заказа в статус «Оплачен» (онлайн-оплата) или «Подтверждён» (наложенный платёж). Заказы, где хотя бы один SKU не синхронизирован или неактивен, не отправляются и попадают в очередь ручного разбора.

**Состав сообщения `order.create`**

| Поле (канон) | Тип | Обяз. | Описание |
| --- | --- | --- | --- |
| `order_number` | string(32) | да | Номер заказа магазина, ключ идемпотентности в WMS |
| `version` | int | да | Версия заказа, растёт при каждом изменении |
| `created_at` | datetime (ISO 8601, UTC) | да | Время создания заказа |
| `priority` | enum | нет | `normal`, `express` — влияет на очередь сборки |
| `delivery.method` | enum | да | `courier`, `pickup_point`, `post` |
| `delivery.carrier_code` | string | да | Код службы доставки по справочнику партнёра |
| `delivery.pickup_point_id` | string | для ПВЗ | Код пункта выдачи |
| `delivery.planned_date` | date | нет | Желаемая дата отгрузки |
| `recipient.name`, `.phone`, `.email` | string | имя и телефон — да | Получатель |
| `recipient.address` | object | для курьера/почты | Индекс, город, улица, дом, квартира, комментарий |
| `lines[].line_id` | string | да | Номер строки заказа |
| `lines[].sku` | string | да | Артикул |
| `lines[].qty` | int | да | Количество, > 0 |
| `lines[].price` | decimal(12,2) | да | Цена за единицу с учётом скидок — для объявленной ценности и чека |
| `payment.cod_amount` | decimal(12,2) | да | Сумма к получению с покупателя; 0 при предоплате |
| `payment.declared_value` | decimal(12,2) | да | Объявленная ценность отправления |
| `comment_for_warehouse` | string(500) | нет | Подарочная упаковка, вложения |
| `documents[]` | object | нет | Ссылки на документы для вложения (накладная, гарантийный талон) |

**Изменение заказа (`order.update`)** — состав, адрес, служба доставки. Разрешено, пока заказ в WMS в статусе «Принят» или «Зарезервирован». Магазин отправляет полный заказ с увеличенным `version`; WMS применяет его целиком или отвечает отказом `ORDER_LOCKED`. При отказе магазин возвращает изменения и сообщает оператору, что заказ уже в сборке.

**Отмена заказа (`order.cancel`)** — запрос, а не команда: WMS отвечает `accepted` или `rejected`.

- До начала сборки — отмена принимается, резерв снимается.
- Во время сборки — WMS по возможности останавливает сборку и возвращает товар в ячейки (статус «Отменён»), либо отказывает.
- После отгрузки — отказ; дальше работает процесс возврата (раздел 8).

Пока ответ на отмену не получен, заказ в магазине находится в статусе «Отмена запрошена», и покупателю не обещается, что посылка не придёт.

## 6. Поток 3: статусы отгрузки (WMS → Shop)

WMS сообщает о каждой смене статуса заказа событием `order.status_changed`; адаптер переводит статусы WMS в канонические ниже, а магазин — в свои статусы. Ключевое событие — «Отгружен»: оно несёт трек-номер и фактический состав отгрузки.

&#91;embedded content: статусная модель заказа · 6 шагов, 3 ответвления\]

Основной путь идёт сверху вниз; отмена принимается из «Принят», «Зарезервирован» и «В сборке» (для сборки — на усмотрение склада), а также из «Недостачи» по решению оператора.

**Маппинг статусов** (соответствие реальным статусам WMS заполняется по документации партнёра)

| Канонический статус | Статус WMS | Статус в магазине | Данные в событии | Покупателю |
| --- | --- | --- | --- | --- |
| `accepted` | уточнить | Передан на склад | ID заказа в WMS | — |
| `rejected` | уточнить | Ошибка передачи на склад | Коды и тексты ошибок по полям | —, задача оператору |
| `reserved` | уточнить | Передан на склад | — | — |
| `shortage` | уточнить | Недостача на складе | Строки и недостающее количество | Оператор связывается с покупателем |
| `picking` | уточнить | Собирается | — | «Заказ собирается» |
| `packed` | уточнить | Собран, ждёт отгрузки | Места, вес | — |
| `shipped` | уточнить | Передан в доставку | Трек-номер, служба доставки, места, `shipped_lines` | «Заказ отправлен» с трек-номером |
| `cancelled` | уточнить | Отменён | Причина | «Заказ отменён» |

**Частичная отгрузка.** Если в `shipped_lines` количество меньше заказанного, магазин помечает неотгруженные позиции, пересчитывает сумму заказа и запускает возврат разницы (предоплата) или корректирует сумму наложенного платежа до отгрузки. Доставка и вручение отслеживаются по трек-номеру через службу доставки и в эту интеграцию не входят.

## 7. Поток 4: остатки (WMS → Shop)

Магазин показывает к продаже свободный остаток WMS минус заказы, которые уже оформлены, но ещё не дошли до склада. Остатки приходят двумя способами: событиями-дельтами в течение дня и полным снапшотом для сверки.

**Формула доступного к продаже количества (считает магазин):**

```latex
\text{Available}_{shop} = \text{Free}_{WMS} - \text{Reserved}_{shop\_not\_sent}
```

где Free WMS — свободный остаток из WMS (без резервов под переданные заказы, брака и блокировок), а Reserved shop not sent — количество в заказах магазина, ещё не принятых WMS. Отрицательный результат приравнивается к нулю, товар снимается с продажи.

| Механизм | Когда | Содержимое | Как применять |
| --- | --- | --- | --- |
| Дельта `stock.changed` | При любом движении на складе (приёмка, резерв, отгрузка, списание, возврат на сток) | `sku`, новое значение `free_qty` (абсолютное, не приращение), `occurred_at`, `seq` | Применить, если `seq` больше последнего применённого по этому SKU, иначе отбросить |
| Снапшот `stock.snapshot` | Ежедневно в 04:00 по времени склада и по запросу | Все SKU: `free_qty`, `reserved_qty`, `damaged_qty`, `as_of` | Перезаписать значения, записать расхождения с текущими в отчёт сверки |
| Запрос по SKU | Перед подтверждением дорогих заказов и по кнопке в админке | `sku[]` → текущий `free_qty` | Обновить точечно |

**Правила:**

- Дельта передаёт абсолютное значение, а не «+3/−1»: потеря или дубль одного события не накапливает ошибку.
- Снапшот, у которого `as_of` старше последней применённой дельты по SKU, не перезаписывает этот SKU.
- Расхождение снапшота и магазина больше 5 единиц или 10% по SKU — повод для алерта: значит, теряются события.
- Если остатки не обновлялись дольше 60 минут, магазин продолжает продажу по последним значениям, но включается алерт.

## 8. Поток 5: возвраты (WMS → Shop)

Склад сообщает о каждой принятой возвратной посылке, а магазин по этому событию проводит возврат денег и обновляет заказ. Возвраты бывают двух видов: невыкуп (посылка не получена и вернулась от службы доставки) и возврат покупателем после получения.

**Событие `return.received`:** `return_id` (WMS), `order_number`, `type` (`not_picked_up` / `customer_return`), `received_at`, `lines[]` с полями `sku`, `qty`, `condition` (`sellable` — вернулся на сток, `damaged` — брак, `incomplete` — некомплект), `comment`, ссылки на фото при браке.

**Обработка в магазине:**

- `sellable` — остаток вырастет сам через `stock.changed`; магазин только фиксирует факт.
- `damaged` / `incomplete` — заказ уходит на ручное решение: полный возврат денег, частичный или претензия к службе доставки.
- Невыкуп переводит заказ в статус «Невыкуп», возврат покупателем — «Возврат получен».
- Возврат без известного `order_number` попадает в очередь ручного разбора.

Регистрация ожидаемого возврата со стороны магазина (заявка на возврат до прихода посылки) — во второй фазе, если WMS её поддерживает.

## 9. Контракты API

В интеграции три контура: внутренние события между магазином и интеграционным сервисом через брокер сообщений, вызовы API WMS из интеграционного сервиса и вебхуки WMS в интеграционный сервис. Пути к API WMS ниже — ожидаемые; точные адреса и форматы берутся из документации партнёра, а адаптер переводит их в каноническую модель.

| Контур | Вызов | Назначение |
| --- | --- | --- |
| Shop → Integration | Топик `shop.items` (событие `item.upserted`) | Карточка товара создана или изменена |
| Shop → Integration | Топик `shop.orders` (`order.ready`, `order.updated`, `order.cancel_requested`) | Команды по заказу |
| Integration → Shop | Топик `wms.events` (`order.status_changed`, `stock.changed`, `stock.snapshot`, `return.received`) | Нормализованные события склада |
| Integration → WMS | `PUT /items/{sku}` | Создать или обновить товар (upsert) |
| Integration → WMS | `POST /orders` | Создать заказ |
| Integration → WMS | `PUT /orders/{order_number}` | Изменить заказ |
| Integration → WMS | `POST /orders/{order_number}/cancel` | Запросить отмену |
| Integration → WMS | `GET /orders/{order_number}` | Статус заказа (опрос, если нет вебхуков, и для сверки) |
| Integration → WMS | `GET /stock?sku=…` и `GET /stock/snapshot` | Остатки по SKU и полный снапшот |
| WMS → Integration | `POST /wms/v1/events` | Вебхук: статусы, остатки, возвраты |

Событийные сообщения в брокере хранятся с ключом партиции `order_number` (для заказов) или `sku` (для остатков) — так сохраняется порядок событий по одному объекту.

**Конверт события (общий для вебхука и топика `wms.events`)**

```json
{
  "event_id": "7f3c2a9e-1b4d-4c8e-9a21-5d6e7f8a9b0c",
  "event_type": "order.status_changed",
  "occurred_at": "2026-10-18T09:42:15Z",
  "seq": 1042,
  "warehouse_id": "MSK-01",
  "payload": { }
}
```

**Пример: создание заказа (`POST /orders`)**

```json
{
  "order_number": "SH-100245",
  "version": 1,
  "created_at": "2026-10-18T09:30:00Z",
  "priority": "normal",
  "delivery": {
    "method": "pickup_point",
    "carrier_code": "CARRIER_A",
    "pickup_point_id": "PVZ-7781"
  },
  "recipient": {
    "name": "Иванова Анна",
    "phone": "+79001234567",
    "email": "anna@example.com"
  },
  "lines": [
    { "line_id": "1", "sku": "TSH-BLK-M", "qty": 2, "price": 1490.00 },
    { "line_id": "2", "sku": "CAP-RED", "qty": 1, "price": 890.00 }
  ],
  "payment": { "cod_amount": 0.00, "declared_value": 3870.00 },
  "comment_for_warehouse": "Подарочная упаковка"
}
```

Ответы WMS: `201` — заказ создан; `200` — заказ с таким `order_number` уже есть (повторная отправка, тело содержит текущее состояние); `409 ORDER_LOCKED` — изменение невозможно; `422` — ошибка валидации со списком полей; `429`/`5xx` — временная ошибка.

**Пример: отгрузка заказа (`order.status_changed`, payload)**

```json
{
  "order_number": "SH-100245",
  "status": "shipped",
  "tracking_number": "CA123456789RU",
  "carrier_code": "CARRIER_A",
  "packages": [ { "package_id": "P1", "weight_g": 640 } ],
  "shipped_lines": [
    { "line_id": "1", "sku": "TSH-BLK-M", "qty": 2 },
    { "line_id": "2", "sku": "CAP-RED", "qty": 1 }
  ]
}
```

**Пример: изменение остатка (`stock.changed`, payload)**

```json
{ "sku": "TSH-BLK-M", "free_qty": 37, "reason": "order_reserved" }
```

Ответ интеграционного сервиса на вебхук: `200` сразу после записи события в журнал, до бизнес-обработки. Повторный `event_id` тоже получает `200` и не обрабатывается второй раз.

## 10. Обработка ошибок, повторы, идемпотентность

Ни одно сообщение не должно теряться и ни одно не должно применяться дважды: временные ошибки повторяются автоматически, бизнес-ошибки сразу уходят на ручной разбор.

| Класс ошибки | Признак | Действие |
| --- | --- | --- |
| Временная | Таймаут, разрыв соединения, `429`, `5xx` | Повтор с экспоненциальной задержкой: 1, 5, 15, 30 мин, затем каждый час до 24 ч. После — DLQ и алерт |
| Бизнес-ошибка | `422`, неизвестный SKU, недопустимый адрес, `409 ORDER_LOCKED` | Без повторов. Заказ получает статус «Ошибка передачи на склад» с текстом ошибки, попадает в очередь оператора |
| Ошибка авторизации | `401`, `403` | Остановить отправку по всему контуру, критический алерт: повторы бессмысленны до замены ключа |
| Некорректное входящее событие | Невалидная схема, неизвестный `order_number` или `sku` | Ответить WMS `200`, сохранить событие в карантин, алерт. Не блокировать поток остальных событий |

**Надёжная отправка из магазина (transactional outbox).** Магазин пишет событие в таблицу outbox в той же транзакции, что и изменение заказа. Отдельный процесс публикует записи в брокер и помечает отправленными. Так событие не теряется при падении сервиса между сохранением заказа и отправкой.

**Идемпотентность:**

- Исходящие: ключ — `order_number` + `version` для заказов, `sku` для товаров. Повтор `POST /orders` с тем же номером не создаёт дубль; если WMS этого не гарантирует, интеграционный сервис перед повтором после таймаута делает `GET /orders/{order_number}`.
- Входящие: таблица обработанных `event_id`, хранение 30 дней. Повторное событие подтверждается и пропускается.

**Порядок событий:**

- События по одному заказу обрабатываются последовательно (партиция по `order_number`).
- Статус, который стоит раньше текущего в статусной модели (например, «В сборке» после «Отгружен»), не применяется, а логируется как предупреждение. Исключения — переходы в «Отменён» и «Недостача», они допустимы из промежуточных статусов.
- Для остатков действует правило `seq` из раздела 7.

## 11. Безопасность

В обмене передаются персональные данные покупателей, поэтому канал шифруется, обе стороны аутентифицируются, а в WMS уходит минимум данных, нужный для доставки.

- **Транспорт:** только HTTPS, TLS 1.2 и выше, в обе стороны.
- **Вызовы в WMS:** OAuth 2.0 client credentials или API-ключ — по возможностям партнёра. Отдельные учётные данные для тестовой и боевой среды.
- **Вебхуки от WMS:** подпись тела HMAC-SHA256 общим секретом в заголовке (например, `X-Signature`) и метка времени `X-Timestamp`; запросы старше 5 минут или с неверной подписью отклоняются с `401`. Дополнительно — список разрешённых IP партнёра.
- **Секреты:** в хранилище секретов (Vault или аналог), не в коде и не в конфигурации репозитория. Ротация раз в 12 месяцев и сразу при подозрении на утечку, без простоя (два действующих ключа на время перехода).
- **Персональные данные:** в WMS передаются только имя, телефон, email и адрес получателя. В логах телефон, email и адрес маскируются. Обработка — по договору поручения с партнёром и требованиям применимого законодательства о персональных данных (152-ФЗ или GDPR — по юрисдикции).
- **Доступ к журналу обмена:** только роли поддержки и разработки, с аудитом просмотров.

## 12. Мониторинг, логирование, сверки

Поддержка должна узнавать о застрявшем заказе раньше покупателя: каждое сообщение пишется в журнал обмена, а алерты срабатывают на задержки, а не только на ошибки.

**Журнал обмена** (хранение 90 дней): направление, тип сообщения, `order_number` / `sku`, `event_id`, `correlation_id`, тело запроса и ответа (с маскированием персональных данных), HTTP-код, номер попытки, время. В карточке заказа в админке — история обмена по нему и кнопка «Отправить повторно».

**Алерты**

| Условие | Порог | Важность |
| --- | --- | --- |
| Заказ не принят WMS после готовности к сборке | 15 мин | Высокая |
| Заказ в статусе «Ошибка передачи на склад» | Любой | Высокая |
| Заказ «Принят» в WMS, но не «Отгружен» после окончания планового дня отгрузки | Плановая дата + 1 рабочий день | Средняя |
| Есть сообщения в DLQ или карантине | Больше 0 | Высокая |
| Нет событий `stock.changed` в рабочее время склада | 60 мин | Средняя |
| Снапшот остатков не пришёл | 1 ч после планового времени | Средняя |
| Ошибки `401`/`403` от WMS | Любая | Критическая |
| Доля временных ошибок вызовов WMS | Больше 5% за 10 мин | Средняя |

**Ежедневные сверки** (отчёт в 06:00):

- Заказы: все заказы магазина, готовые к сборке за последние 7 дней, против списка заказов WMS — нет в WMS, лишние в WMS, расхождение статусов.
- Остатки: снапшот против значений магазина по каждому SKU, с порогом расхождения из раздела 7.
- Отгрузки: отгруженные заказы без трек-номера.

**Метрики:** время от готовности заказа до приёма WMS (p50, p95), время от события на складе до обновления в магазине, количество сообщений по типам, глубина очередей.

## 13. Нефункциональные требования

Целевые значения ниже — предложение аналитика; их нужно сверить с реальными объёмами магазина и лимитами API партнёра (раздел 15).

| Показатель | Цель | Комментарий |
| --- | --- | --- |
| Задержка передачи заказа на склад | p95 ≤ 2 мин, максимум 5 мин | От готовности к сборке до ответа WMS «принят» |
| Задержка статуса в магазине | p95 ≤ 5 мин | От события в WMS до обновления заказа |
| Задержка обновления остатков | p95 ≤ 5 мин | При опросе вместо вебхуков — интервал опроса не больше 5 мин |
| Пиковая нагрузка | 10 × средний часовой поток заказов | Распродажи; уточнить фактический объём |
| Доступность интеграционного сервиса | 99,5% в месяц | Не более 3,6 ч простоя |
| Устойчивость к недоступности WMS | Без потерь при простое до 72 ч | Очереди копят сообщения и отправляют после восстановления в исходном порядке |
| Соблюдение лимитов WMS | Не превышать rate limit партнёра | Ограничитель скорости на стороне интеграционного сервиса |
| Время восстановления после сбоя сервиса | ≤ 30 мин | Сервис без состояния, состояние в БД и брокере |

Интеграционный сервис масштабируется горизонтально; порядок по одному заказу обеспечивается партиционированием, а не единственным экземпляром обработчика.

## 14. Тестирование и приёмка

Интеграция принимается после прохождения сценариев ниже на тестовой среде партнёра и двухнедельного пилота на части заказов в бою.

**Этапы:**

1. Контрактные тесты адаптера WMS на примерах сообщений из документации партнёра и из раздела 9.
2. Интеграционные тесты на тестовой среде (sandbox) WMS по сценариям ниже.
3. Нагрузочный тест: пиковый поток из раздела 13 в течение 1 часа без роста задержек выше целевых.
4. Пилот: 10% заказов (или один способ доставки) через интеграцию 2 недели, ежедневная сверка, затем 100%.
5. План отката: флаг отключения автоматической передачи; заказы возвращаются к ручному процессу без потерь.

**Обязательные сценарии**

- [ ] Новый товар синхронизируется, заказ по нему принимается WMS
- [ ] Заказ с несинхронизированным SKU не уходит и попадает в очередь оператора
- [ ] Полный цикл: заказ → принят → в сборке → упакован → отгружен, трек-номер в магазине
- [ ] Частичная отгрузка при недостаче: магазин получает фактический состав
- [ ] Изменение адреса до сборки принимается; после начала сборки — отказ `ORDER_LOCKED`
- [ ] Отмена до сборки, во время сборки (принята и отклонена), после отгрузки (отказ)
- [ ] Повторная отправка того же заказа не создаёт дубль
- [ ] Повтор вебхука с тем же `event_id` не обрабатывается дважды
- [ ] События пришли не по порядку: устаревший статус и устаревший остаток отброшены
- [ ] WMS недоступна 1 час: заказы копятся и уходят после восстановления, без потерь и дублей
- [ ] Неверная подпись вебхука — отказ `401`
- [ ] Снапшот остатков обновляет значения и формирует отчёт о расхождениях
- [ ] Невыкуп и возврат покупателем (годный и брак) корректно отражаются в заказе
- [ ] Алерты срабатывают на каждое условие из раздела 12

**Критерии приёмки пилота:** 0 потерянных и 0 задублированных заказов; расхождения остатков по ежедневной сверке не выше порога из раздела 7; задержки в пределах целей раздела 13.

## 15. Открытые вопросы

Ответы на эти вопросы закрывают допущения раздела 2; до их получения можно разрабатывать каноническую модель, outbox, журнал и логику магазина, но не адаптер WMS.

**К логистическому партнёру**

- [ ] Тип API (REST, SOAP, обмен файлами по SFTP), документация, тестовая среда, способ аутентификации
- [ ] Есть ли вебхуки; какие события они покрывают; гарантируется ли доставка и с какими повторами
- [ ] Полный список статусов заказа в WMS и их точное значение
- [ ] Идемпотентен ли приём заказа по внешнему номеру
- [ ] До какого статуса можно изменить и отменить заказ
- [ ] Как WMS обрабатывает недостачу: ждёт поступления, отгружает частично или отклоняет
- [ ] Как передаётся остаток: свободный или физический; есть ли порядковый номер событий; расписание снапшота
- [ ] Лимиты API (запросов в секунду, размер пакета)
- [ ] Справочник кодов служб доставки, кто формирует этикетки и когда появляется трек-номер
- [ ] Время отсечки (cut-off): до какого часа принятый заказ отгружается в тот же день
- [ ] Поддержка серийных номеров, кодов маркировки, сроков годности
- [ ] Регламент плановых работ и контакты дежурной поддержки

**К бизнесу**

- [ ] Средний и пиковый объём заказов в день и в час, число активных SKU
- [ ] Нужна ли частичная отгрузка или заказ ждёт полной комплектации
- [ ] Кто и в какие сроки разбирает очередь ошибок передачи
- [ ] Нужны ли приоритетные (экспресс) заказы и подарочная упаковка в первой версии
- [ ] Правила возврата денег при браке и некомплекте
