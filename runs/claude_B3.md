## 1. Вопросы к заказчику

Ответы на эти вопросы определяют правила передачи заказов, статусную модель и требования к нагрузке. Пока ответов нет, в спецификации стоят допущения из раздела 3, помеченные «подтвердить».

2. Какой срок отгрузки обещан покупателю? Есть ли время отсечки (например, «заказ до 14:00 — отгрузка сегодня»)?
3. Когда нужно запуститься и есть ли жёсткие даты (сезон, договор со складом)?

**Заказы**

4. Какие заказы уходят на склад: все или только оплаченные? Как быть с оплатой при получении?

6. Можно ли менять заказ после передачи на склад (состав, адрес, способ доставки)? До какого момента разрешена отмена?
7. Допустима ли частичная отгрузка, если части товара нет? Или заказ ждёт полной комплектации?

## 3. Цели, границы и допущения

Интеграция без участия оператора передаёт заказы в WMS, возвращает в магазин статусы отгрузки с трек-номером и поддерживает на сайте актуальные остатки. Первая версия включает пять потоков, перечисленных ниже.

**Входит в первую версию**

| Поток | Направление | Мастер данных |
| --- | --- | --- |
| П1. Справочник товаров | Магазин → WMS | Магазин |
| П2. Передача заказа | Магазин → WMS | Магазин |
| П3. Отмена заказа | Магазин → WMS | Магазин (решение), WMS (возможность) |
| П4. Статусы отгрузки и трек-номер | WMS → Магазин | WMS |
| П5. Остатки | WMS → Магазин | WMS |

**Не входит в первую версию:** возвраты и невыкупы, приёмка поставок, статусы последней мили, биллинг услуг склада. Если заказчик включит их в объём (вопросы 1.11–1.12), они оформляются отдельной итерацией.

**Допущения (подтвердить)**

- WMS предоставляет REST API с форматом JSON и тестовый контур.
- WMS отправляет webhooks о смене статуса; если нет, используется опрос (раздел 5, П4).
- Склад один; все даты передаются в UTC в формате ISO 8601.
- На склад уходят оплаченные заказы и заказы с оплатой при получении, подтверждённые оператором.
- Изменение состава заказа после передачи не поддерживается: только отмена и создание нового заказа.
- Номер заказа магазина уникален и не меняется; он служит ключом идемпотентности.

**Глоссарий**

| Термин | Значение |
| --- | --- |
| Магазин | Собственная платформа интернет-магазина |
| WMS | Система управления складом логистического партнёра |
| ИС | Интеграционный сервис — отдельный компонент, через который идёт весь обмен |
| SKU | Артикул товара, единый для магазина и WMS |
| Отгрузка | Передача собранного заказа в службу доставки, одна или несколько посылок |
| Доступный остаток | Количество, которое можно продать на сайте (формула в П5) |
| Outbox | Таблица исходящих событий в базе магазина, пишется в одной транзакции с заказом |
| DLQ | Очередь сообщений, которые не удалось обработать после всех повторов |

## 4. Архитектура и участники

Магазин и WMS не вызывают друг друга напрямую: весь обмен идёт через отдельный интеграционный сервис (ИС). Так смена WMS или её API затрагивает только адаптер ИС, а сбои склада не блокируют оформление заказов.

&#91;embedded content: архитектура интеграции · 3 системы, 4 компонента ИС\]

Исходящие события магазин пишет в outbox в одной транзакции с заказом, поэтому событие не теряется при сбое между записью заказа и отправкой. Входящие данные ИС применяет через внутренние API магазина. Очереди ИС партиционируются по номеру заказа (раздел 8). ИС может быть модулем платформы, если сохраняются отдельные очереди, журнал и админка.

## 5. Сценарии потоков данных

Каждый поток работает асинхронно через ИС; магазин никогда не ждёт ответа WMS в пользовательском запросе. Доставка сообщений — «как минимум один раз», дубли гасятся идемпотентностью (раздел 8).

### П1. Справочник товаров (магазин → WMS)

Триггер: создание SKU или изменение его складских атрибутов (название, штрихкоды, вес, габариты, признак маркировки).

1. Магазин пишет событие `product.upserted` в outbox.
2. ИС отправляет карточку в WMS методом создания или обновления по SKU.
3. Успех: ИС отмечает SKU как синхронизированный (`wms_synced_at`).
4. Ошибка валидации: SKU помечается «не синхронизирован», уведомление контент-менеджеру. Заказы с таким SKU не передаются (П2, шаг 3).

При запуске выполняется первичная выгрузка всего каталога пакетами.

### П2. Передача заказа (магазин → WMS)

Триггер: заказ перешёл в статус «Готов к отгрузке» (оплачен или подтверждён оператором для оплаты при получении).

1. Магазин в той же транзакции, что и смену статуса, пишет событие `order.ready_for_fulfillment` в outbox.
2. ИС забирает событие, загружает заказ, строит запрос по маппингу (раздел 7).
3. ИС проверяет данные: все SKU синхронизированы, обязательные поля заполнены, длины полей в лимитах WMS.
4. ИС отправляет заказ в WMS с ключом идемпотентности = номер заказа.
5. Успех: ИС сохраняет `wms_order_id`, заказ в магазине получает статус «Передан на склад».
6. Ошибка данных (4xx): статус «Ошибка передачи», уведомление оператору. Оператор исправляет заказ и запускает повтор из админки.
7. Временная ошибка (таймаут, 5xx, 429): повторы по политике раздела 8, после исчерпания — DLQ и алерт.

Цель: заказ попадает в WMS не позднее 5 минут после события (p95).

### П3. Отмена заказа (магазин → WMS)

Триггер: отмена заказа в магазине, когда он уже передан на склад.

1. Магазин пишет событие `order.cancel_requested`; статус заказа — «Отмена запрошена».
2. ИС вызывает отмену в WMS по `wms_order_id`.
3. WMS подтвердила: статус «Отменён», резерв возвращается в остаток через П5.
4. WMS отказала (заказ уже собран или отгружен): статус «Отмена отклонена», уведомление оператору. Дальше заказ обрабатывается как возврат вне интеграции.

Если заказ ещё не передан (событие П2 в очереди), ИС отменяет его локально и не отправляет в WMS.

### П4. Статусы отгрузки (WMS → магазин)

Основной канал — webhooks WMS; резервный — опрос.

1. WMS отправляет событие на эндпоинт ИС.
2. ИС проверяет подпись, сохраняет событие во входящую таблицу и сразу отвечает 200. Дубликат по `event_id` — тоже 200, без обработки.
3. Обработчик сопоставляет статус WMS со статусом магазина (раздел 6) и применяет его, если он не «старше» текущего.
4. При статусе «Отгружен» ИС передаёт в магазин трек-номер, службу доставки и отгруженные количества по позициям. Магазин уведомляет покупателя.
5. Резервный опрос: каждые 15 минут ИС запрашивает статусы незавершённых заказов, изменённых с момента последнего опроса.

Если WMS не поддерживает webhooks, шаг 5 становится основным, интервал — 5 минут.

### П5. Остатки (WMS → магазин)

WMS — мастер остатков. Используются два механизма:

1. Изменения: события об изменении остатка (webhook) или опрос изменений каждые 5–10 минут.
2. Полный снимок: раз в сутки ночью ИС загружает все остатки, сравнивает с магазином и исправляет расхождения с записью в отчёт.

Доступный остаток на сайте рассчитывается в ИС:

```latex
\text{Доступно} = \text{Доступно}_{WMS} - \text{Заказы в пути} - \text{Страховой запас}
```

«Заказы в пути» — количество по заказам, созданным в магазине, но ещё не принятым WMS. Если WMS не вычитает принятые несобранные заказы (вопрос 2.20), их тоже нужно вычесть. Отрицательный результат приравнивается к нулю. Обновление применяется, только если метка времени или версия новее последней применённой по этому SKU.

## 6. Статусная модель

ИС ведёт собственный статус выполнения заказа и переводит в него статусы WMS; статус движется только вперёд по рангу. Отмена доступна из статусов «Передан на склад», «Принят складом» и «В сборке»; фактическое окно отмены зависит от WMS (вопрос 2.13).

Коды WMS в таблице условные: после получения списка статусов от партнёра (вопрос 2.16) колонка заполняется реальными кодами. Неизвестный код WMS не меняет статус заказа: он пишется в журнал и вызывает алерт.

| Статус магазина | Ранг | Условный код WMS | Что видит покупатель | Действие ИС |
| --- | --- | --- | --- | --- |
| Готов к отгрузке | 10 | — | «Готовится к отправке» | Передать заказ (П2) |
| Передан на склад | 20 | успешный ответ на создание | «Готовится к отправке» | Сохранить `wms_order_id` |
| Принят складом | 30 | `ACCEPTED` | «Готовится к отправке» | — |
| Ожидает товар (если есть в WMS) | 35 | `BACKORDER` | «Готовится к отправке» | Алерт оператору через 24 ч в статусе |
| В сборке | 40 | `PICKING`, `PACKED` | «Собирается» | — |
| Частично отгружен | 55 | `PARTIALLY_SHIPPED` | «Часть заказа отправлена» + трек | Передать трек и отгруженные позиции |
| Отгружен | 60 | `SHIPPED` | «Передан в доставку» + трек | Передать трек и отгруженные позиции |
| Ошибка передачи | — | ответ 4xx на создание | «Готовится к отправке» | Уведомить оператора |
| Отмена запрошена | — | — | «Отменяется» | Вызвать отмену в WMS (П3) |
| Отменён | 100 | `CANCELLED` | «Отменён» | Пересчитать остаток SKU |
| Отмена отклонена | — | отказ в отмене | решает оператор | Уведомить оператора |

Правила переходов: событие с рангом ниже текущего игнорируется. Статусы без ранга выставляет сама ИС, они не блокируют последующие события WMS. Если после «Отмена запрошена» приходит `SHIPPED`, заказ получает «Отгружен» и оператор получает уведомление.

## 7. Модели данных и контракты API

ИС работает с каноническими моделями ниже; адаптер WMS переводит их в формат партнёра. Имена эндпоинтов WMS условные и заменяются по документации партнёра (вопрос 2.1), канонические модели при этом не меняются.

### 7.1. Интерфейсы

| Направление | Вызов | Назначение | Поток |
| --- | --- | --- | --- |
| ИС → WMS | `PUT /products/{sku}` | Создать или обновить карточку товара | П1 |
| ИС → WMS | `POST /orders` | Создать заказ на отгрузку | П2 |
| ИС → WMS | `POST /orders/{wms_order_id}/cancel` | Отменить заказ | П3 |
| ИС → WMS | `GET /orders?updated_since=` | Резервный опрос статусов | П4 |
| WMS → ИС | `POST /webhooks/wms` | События статусов и остатков | П4, П5 |
| ИС → WMS | `GET /stock?updated_since=` / `GET /stock` | Изменения остатков / полный снимок | П5 |
| ИС → Магазин | `PATCH /internal/orders/{order_number}/fulfillment` | Обновить статус, трек-номер, отгруженные позиции | П4 |
| ИС → Магазин | `PUT /internal/stock` (пакет) | Обновить доступные остатки | П5 |

| `delivery.carrier_code` | `order.shipping_method` | Да | По справочнику соответствия способов доставки |
| `recipient.phone` | `order.customer_phone` | Да | Нормализовать в E.164 |

| `payment.type` | `order.payment_method` | Да | `prepaid` или `cod`; для `cod` обязателен `cod_amount` |
| `items[].sku` | `order_line.sku` | Да | SKU должен иметь `wms_synced_at` |
| `items[].quantity` | `order_line.qty` | Да | Целое > 0; комплекты раскладываются на компоненты, если WMS не знает комплектов |
| `declared_value` | `order.total - order.shipping_cost` | Нет | Для страховки отправления |

## 8. Ошибки, повторы, идемпотентность

Повторяются только временные ошибки; ошибки данных сразу уходят оператору, потому что повтор их не исправит.

| Тип ошибки | Пример | Действие ИС |
| --- | --- | --- |
| Временная | Таймаут, обрыв связи, HTTP 5xx | Повтор с экспоненциальной задержкой |
| Перегрузка | HTTP 429 | Повтор после `Retry-After`, иначе по общей политике |
| Дубликат | HTTP 409 «заказ уже существует» | Считать успехом, запросить `wms_order_id` по номеру заказа |
| Неизвестный SKU | WMS не знает артикул | Выполнить П1 для SKU и повторить заказ один раз |
| Ошибка данных | HTTP 400/422: пустой адрес, длинное поле | Без повтора: статус «Ошибка передачи», уведомление оператору |
| Авторизация | HTTP 401/403 | Остановить отправку, критический алерт |
| Недоступность ИС для webhook | WMS не получила 200 | Полагаемся на повторы WMS и резервный опрос (П4, шаг 5) |

**Политика повторов.** Задержки: 1, 2, 4, 8, 16, 32, 60, 60 минут (8 попыток, около 3 часов), со случайным разбросом ±20%. После последней попытки сообщение уходит в DLQ, создаётся алерт. Из DLQ сообщение возвращается в обработку кнопкой в админке. Таймаут одного запроса к WMS — 30 секунд.

**Идемпотентность**

- Исходящие заказы: ключ идемпотентности = `order_number`. Если WMS не поддерживает ключ, ИС перед повтором после таймаута проверяет наличие заказа по номеру.
- Входящие события: уникальный индекс по `event_id` в `inbound_event`; повтор — ответ 200 без обработки.
- Статусы: у каждого статуса магазина есть ранг. Событие с рангом ниже текущего не применяется, только записывается в журнал. Исключения — переходы в «Отменён» и «Ошибка» по правилам раздела 6.
- Остатки: обновление по SKU применяется, только если `updated_at` новее сохранённого `source_updated_at`.

**Порядок обработки.** События одного заказа обрабатываются строго последовательно (партиционирование очереди по `order_number`). Разные заказы — параллельно. Если событие статуса пришло раньше, чем ИС сохранила `wms_order_id`, оно сопоставляется по `order_number`.

## 9. Безопасность, мониторинг, сверка

Любой заказ, застрявший в интеграции, должен быть обнаружен автоматически в пределах часа, а расхождения данных — устранены ежедневной сверкой.

**Безопасность**

- Весь обмен по HTTPS, TLS 1.2 и выше.
- Доступ к WMS — по механизму партнёра (OAuth 2.0 client credentials или API-ключ). Секреты хранятся в хранилище секретов, не в коде и не в конфигурации репозитория.
- Webhooks: подпись HMAC-SHA256 тела запроса и метки времени, окно допустимости 5 минут, белый список IP-адресов партнёра (если партнёр его даёт).
- Внутренние вызовы ИС → магазин — по служебному токену с минимальными правами (только статусы заказов и остатки).
- Персональные данные: передаётся только то, что нужно для доставки (имя, телефон, адрес, email — если требует служба доставки). В журналах телефон, email и адрес маскируются.
- Правовое основание передачи персональных данных складу фиксируется в договоре с партнёром (вопрос 1.20).

**Мониторинг и алерты**

| Условие | Порог | Важность |
| --- | --- | --- |
| Заказ в «Готов к отгрузке» без передачи в WMS | > 15 минут | Высокая |
| Сообщения в DLQ | > 0 | Высокая |
| Ошибки авторизации в WMS | Любая | Критическая |
| Заказ «Передан на склад» без подтверждения приёма | > 1 часа | Средняя |
| Заказ принят, но не отгружен после срока отгрузки | Срок из ответа 1.2 | Средняя |
| Нет входящих webhooks в рабочие часы склада | > 2 часов | Средняя |
| Остатки не обновлялись | > 3 интервалов опроса | Высокая |
| Доля ошибок вызовов WMS | > 5% за 15 минут | Высокая |

Метрики выводятся на дашборд: число заказов по статусам интеграции, задержка передачи и статусов (p50, p95), размер очередей и DLQ.

**Журналирование.** Каждый запрос и ответ пишется в `exchange_log` с `correlation_id` = номер заказа (или SKU для остатков и товаров). Хранение — 90 дней.

**Сверка**

- Статусы: раз в час ИС запрашивает в WMS статусы всех незавершённых заказов старше 1 часа и исправляет расхождения.
- Остатки: ночной полный снимок (П5) с отчётом о расхождениях больше 0 единиц по SKU.
- Заказы: раз в сутки сверка списка заказов за прошлые сутки между магазином и WMS; заказы, которые есть только в одной системе, — в отчёт оператору.

**Админка интеграции:** поиск по номеру заказа или SKU, история обмена по заказу, ручной повтор передачи, повтор из DLQ, принудительная синхронизация остатка SKU.

## 10. Нефункциональные требования, тестирование, приёмка

Целевые значения ниже — стартовые; пиковую нагрузку и сроки уточняем после ответов на вопросы 1.1–1.2 и 2.4, 2.8.

**Нефункциональные требования**

| Показатель | Целевое значение |
| --- | --- |
| Задержка передачи заказа в WMS | ≤ 5 мин, p95 |
| Задержка статуса в магазине (webhook) | ≤ 5 мин после события в WMS, p95 |
| Задержка статуса в магазине (опрос) | ≤ 20 мин |
| Актуальность остатков на сайте | ≤ 15 мин |
| Пиковая нагрузка | 10× среднего дня без роста задержек выше целевых |
| Восстановление после простоя WMS 4 часа | Очередь разбирается ≤ 1 часа после возврата WMS, без потерь |
| Доступность приёмника webhooks | 99,5% в месяц |
| Потеря заказов и событий | 0 (outbox + повторы + сверка) |

**Тестирование**

- Модульные тесты маппинга и статусной модели, включая недопустимые переходы.
- Контрактные тесты адаптера против тестового контура WMS.
- Нагрузочный тест на пиковый объём.
- Тесты отказов: WMS недоступна, отвечает 429, присылает дубли и события не по порядку.

**Сценарии приёмки**

| ID | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| A1 | Оплаченный заказ из двух позиций | В WMS за ≤ 5 мин, статус «Передан на склад», затем «Отгружен» с трек-номером |
| A2 | Повторная отправка того же заказа | В WMS один заказ |
| A3 | Заказ с неизвестным SKU | SKU синхронизирован, заказ передан |
| A4 | Заказ с пустым адресом | «Ошибка передачи», уведомление оператору, повтор после исправления |
| A5 | Отмена до сборки | «Отменён», остаток вернулся на сайт |
| A6 | Отмена после отгрузки | «Отмена отклонена», уведомление оператору |
| A7 | Частичная отгрузка | «Частично отгружен», отгруженные количества по позициям |
| A8 | Webhook-дубль и события не по порядку | Статус не откатывается, дубль не обрабатывается |
| A9 | WMS недоступна 1 час | Заказы переданы после восстановления, без дублей |
| A10 | Ночная сверка остатков с расхождением | Расхождение исправлено и попало в отчёт |

**Решения, ожидающие ответов**

- Тип API WMS и наличие webhooks (2.1, 2.5) — определяют адаптер и основной канал П4.
- Правило и окно отмены (1.6, 2.13).
- Частичные отгрузки (1.7, 2.12, 2.18) — нужен ли статус «Частично отгружен» и несколько трек-номеров.
- Формула доступного остатка и страховой запас (1.13, 2.19–2.20).
- Объём первой версии: возвраты, поставки, статусы доставки (1.11–1.12, 2.22).
