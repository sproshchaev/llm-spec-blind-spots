# Спецификация интеграции интернет-магазина с WMS логистического партнёра

Oct 18, 2026 · Версия 0.1 (черновик)

## 1. Назначение и границы

Интеграция автоматически передаёт готовые к отгрузке заказы магазина в WMS логистического партнёра и возвращает в магазин статусы отгрузки, трек-номера и остатки. Ручные выгрузки и сверки в Excel уходят; целевая задержка по каждому потоку — минуты (см. раздел 12).

Документ адресован разработчикам магазина и интеграционного сервиса. Протокол API партнёра пока неизвестен, поэтому спецификация описывает канонический (наш) формат данных, а преобразование в формат WMS вынесено в отдельный адаптер. Всё, что нужно уточнить у партнёра, собрано в разделе 14.

**Входит в объём:**

- синхронизация номенклатуры (SKU, штрихкоды, весогабариты) — обязательное условие для передачи заказов;
- создание заказа на отгрузку в WMS;
- отмена и изменение заказа до начала сборки;
- статусы исполнения, трек-номера, частичная отгрузка;
- остатки: события изменений и ежедневный полный снимок;
- возвраты и невыкупы — приёмка на склад и состояние товара.

**Не входит:** приёмка поставок от поставщиков на склад (ASN — кандидат во второй этап), биллинг услуг склада, прямая интеграция со службами доставки (предполагается, что груз в доставку передаёт партнёр), платежи.

## 2. Участники, термины, мастер-данные

В интеграции три системы; новая из них одна — интеграционный сервис на нашей стороне.

| Участник | Роль в интеграции | Владелец |
| --- | --- | --- |
| Магазин (Shop) | Источник заказов и карточек товаров; потребитель статусов и остатков | Наша команда |
| Интеграционный сервис (IS) | Новый компонент: очереди, преобразование форматов, повторы, журнал, сверки | Наша команда |
| Адаптер WMS | Часть IS: перевод канонической модели в протокол партнёра и обратно | Наша команда |
| WMS партнёра | Исполнение отгрузки, учёт физических остатков, передача в доставку | Логистический партнёр |

Кто является источником истины по каждому типу данных. При расхождении побеждает мастер-система.

| Данные | Мастер-система | Направление |
| --- | --- | --- |
| Карточка товара, SKU, штрихкоды | Магазин | Shop → WMS |
| Заказ (состав, получатель, адрес) | Магазин | Shop → WMS |
| Статус исполнения, трек-номер | WMS | WMS → Shop |
| Физический остаток на складе | WMS | WMS → Shop |
| Остаток, доступный к продаже на сайте | Магазин (рассчитывает по данным WMS) | — |

**Термины:**

- **SKU** — артикул товара, общий ключ для обеих систем; после передачи в WMS не меняется.
- **Заказ на отгрузку** — документ в WMS, созданный из заказа магазина; связь через `external_order_id`.
- **Доступный остаток** — годный товар на складе минус товар, зарезервированный под заказы.
- **Outbox** — таблица в БД магазина, куда событие пишется в одной транзакции с изменением заказа; гарантирует, что событие не потеряется.
- **DLQ** (dead letter queue) — очередь сообщений, которые не удалось обработать после всех повторов; разбираются вручную.

## 3. Архитектура и способ взаимодействия

Магазин и WMS не вызывают друг друга напрямую: весь обмен идёт через интеграционный сервис, а особенности протокола партнёра изолированы в адаптере. Смена партнёра или его API затрагивает только адаптер.

&#91;embedded content: архитектура интеграции · 3 системы, 4 потока\]

События магазина попадают в outbox и через очередь доходят до обработчиков; адаптер отправляет вызовы в API партнёра и принимает его события, а результаты возвращаются в магазин через внутренний API.

| Взаимодействие | Механизм | Операции |
| --- | --- | --- |
| Shop → IS | Outbox + брокер сообщений (RabbitMQ или Kafka — по стеку команды) | `product.upserted`, `order.ready_for_fulfillment`, `order.cancel_requested` |
| IS → Shop | Внутренний REST API магазина | `PUT /internal/orders/{external_order_id}/fulfillment`, `PUT /internal/stock`, `POST /internal/orders/{external_order_id}/returns` |
| IS → WMS | API партнёра через адаптер | Создание и отмена заказа, карточки товаров, запрос статусов и остатков |
| WMS → IS | Webhooks `POST /wms/webhooks/{event_type}`; при их отсутствии — опрос | Статусы, остатки, возвраты |

Каждое сообщение в канонической модели имеет общий конверт: `event_id` (UUID), `event_type`, `schema_version`, `occurred_at` (ISO 8601, UTC), `correlation_id`. Все даты передаются в UTC, суммы — decimal с двумя знаками, валюта магазина фиксирована в настройках.

## 4. Поток 0: номенклатура (Shop → WMS)

Заказ с товаром, которого нет в WMS, склад отклонит, поэтому карточка товара должна попасть в WMS раньше первого заказа с ней. До запуска выполняется полная начальная выгрузка каталога; дальше — передача изменений.

**Триггер:** создание товара или изменение любого поля из таблицы ниже. Магазин пишет событие `product.upserted` в outbox. Изменения цены, описаний и фото складу не передаются.

| Поле | Тип | Обяз. | Правила |
| --- | --- | --- | --- |
| `sku` | string(50) | да | Уникален, неизменяем. Новый артикул — новая карточка |
| `name` | string(255) | да | Название для комплектовщика и документов |
| `barcodes` | string\[\] | да | EAN-13 / EAN-8 / Code128; минимум один |
| `unit` | enum | да | `pcs`, `set`, `kg` |
| `weight_g` | int | да | Вес брутто единицы, граммы |
| `length_mm`, `width_mm`, `height_mm` | int | да | Габариты в упаковке, миллиметры |
| `is_fragile` | bool | нет | Влияет на упаковку |
| `shelf_life_days` | int | нет | Если задан — WMS ведёт учёт по срокам годности |
| `marking_required` | bool | нет | Требуется сканирование кодов маркировки или серийных номеров при отгрузке |
| `is_active` | bool | да | `false` — товар выведен; новые заказы с ним не передаются |

```json
{
  "event_id": "0f6c1c2e-7a5b-4c1e-9f0a-2b1d3e4f5a6b",
  "event_type": "product.upserted",
  "occurred_at": "2026-10-18T10:15:00Z",
  "product": {
    "sku": "TSH-0042-BLK-M",
    "name": "Футболка базовая, чёрная, M",
    "barcodes": ["4601234567890"],
    "unit": "pcs",
    "weight_g": 220,
    "length_mm": 300, "width_mm": 250, "height_mm": 20,
    "is_fragile": false,
    "marking_required": false,
    "is_active": true
  }
}
```

**Правила:**

- IS хранит статус синхронизации по каждому SKU (`pending`, `synced`, `error`). Заказ, где есть SKU не в статусе `synced`, задерживается до синхронизации, а не отправляется с заведомой ошибкой.
- Удаления карточек нет: товар деактивируется через `is_active = false`.
- Ошибка валидации на стороне WMS (например, дубль штрихкода) — в DLQ и уведомление ответственному за каталог.

## 5. Поток 1: заказы (Shop → WMS)

Заказ уходит на склад в момент перехода в статус «Готов к отгрузке» и должен быть принят WMS не позже чем через 2 минуты (p95). Какое событие переводит заказ в этот статус (оплата, подтверждение оператором, подтверждение наложенного платежа), решает бизнес — см. раздел 14.

**Последовательность:**

1. Магазин меняет статус заказа и в той же транзакции пишет событие `order.ready_for_fulfillment` в outbox.
2. IS забирает событие, проверяет, что все SKU синхронизированы, валидирует заказ.
3. Адаптер преобразует заказ в формат WMS и отправляет его.
4. WMS отвечает: принят (возвращает свой `wms_order_id`) или отклонён (код ошибки).
5. IS сообщает результат магазину: заказ получает статус «Передан на склад» или «Ошибка передачи».

**Состав заказа:**

| Поле | Тип | Обяз. | Правила |
| --- | --- | --- | --- |
| `external_order_id` | string(50) | да | Номер заказа в магазине. Ключ идемпотентности |
| `created_at` | datetime (ISO 8601, UTC) | да | Время создания заказа |
| `priority` | enum | нет | `normal`, `express` |
| `delivery.method` | enum | да | `courier`, `pickup_point`, `post`; справочник согласовать с партнёром |
| `delivery.carrier_code` | string | да | Код службы доставки из справочника партнёра |
| `delivery.pickup_point_id` | string | усл. | Обязателен для `pickup_point` |
| `delivery.planned_date` | date | нет | Желаемая дата передачи в доставку |
| `recipient.full_name` | string(255) | да |  |
| `recipient.phone` | string | да | Формат E.164: `+79001234567` |
| `recipient.email` | string | нет |  |
| `address` | object | усл. | Структурно: страна, индекс, регион, город, улица, дом, квартира; обязателен для курьера и почты |
| `lines[].line_id` | string | да | Номер строки, уникален в заказе |
| `lines[].sku` | string | да | Только синхронизированные SKU |
| `lines[].qty` | int > 0 | да |  |
| `lines[].price` | decimal(12,2) | да | Цена за единицу с учётом скидок — для документов и объявленной ценности |
| `payment.cod_amount` | decimal(12,2) | да | Сумма наложенного платежа; `0` для предоплаты |
| `payment.declared_value` | decimal(12,2) | да | Объявленная ценность отправления |
| `comment` | string(500) | нет | Комментарий для склада |

```json
{
  "event_id": "8d2a4b6c-1e3f-4a5b-8c7d-9e0f1a2b3c4d",
  "event_type": "order.ready_for_fulfillment",
  "occurred_at": "2026-10-18T10:20:00Z",
  "order": {
    "external_order_id": "SH-1045872",
    "created_at": "2026-10-18T10:05:12Z",
    "priority": "normal",
    "delivery": {"method": "courier", "carrier_code": "CDEK", "planned_date": "2026-10-19"},
    "recipient": {"full_name": "Иванова Анна", "phone": "+79001234567", "email": "anna@example.com"},
    "address": {"country": "RU", "postcode": "620014", "city": "Екатеринбург", "street": "ул. Малышева", "house": "51", "flat": "12"},
    "lines": [
      {"line_id": "1", "sku": "TSH-0042-BLK-M", "qty": 2, "price": 1490.00}
    ],
    "payment": {"cod_amount": 0, "declared_value": 2980.00},
    "comment": ""
  }
}
```

**Ответы WMS и реакция:**

| Ответ (канонический код) | Повторять? | Статус в магазине | Действие |
| --- | --- | --- | --- |
| `ACCEPTED` | — | Передан на склад | Сохранить `wms_order_id` |
| `DUPLICATE` | нет | Передан на склад | Считать успехом: заказ уже в WMS, взять существующий `wms_order_id` |
| `UNKNOWN_SKU` | после синхронизации | Ожидает склада | Запустить синхронизацию SKU, повторить |
| `INSUFFICIENT_STOCK` | нет | Ошибка передачи | Уведомить оператора; решение — частичная отгрузка или отмена |
| `INVALID_ADDRESS`, `VALIDATION_ERROR` | нет | Ошибка передачи | В DLQ, оператор исправляет заказ и отправляет повторно |
| Таймаут, HTTP 5xx, 429 | да | Ожидает склада | Повтор по правилам раздела 9 |

Коды WMS партнёра сводятся к каноническим в адаптере; таблица соответствия заполняется после получения документации партнёра.

## 6. Поток 2: статусы отгрузки (WMS → Shop)

Каждое изменение статуса заказа в WMS должно появиться в магазине не позже чем через 5 минут. Предпочтительный способ — webhook от WMS в IS; если партнёр его не поддерживает, IS опрашивает WMS каждые 5 минут по заказам в незавершённых статусах.

**Соответствие статусов:**

| Канонический статус | Статус в магазине | Дополнительные данные | Действие в магазине |
| --- | --- | --- | --- |
| `ACCEPTED` | Передан на склад | `wms_order_id` | — |
| `PICKING` | Собирается | — | Отмена через WMS ещё возможна (уточнить окно) |
| `PACKED` | Собран | Места: вес, габариты | — |
| `SHIPPED` | Передан в доставку | Трек-номер, служба доставки, отгруженные строки | Письмо/SMS клиенту с трек-номером |
| `PARTIALLY_SHIPPED` | Отгружен частично | Отгруженные строки, недостача | Уведомить оператора и клиента; частичный возврат денег |
| `CANCELLED` | Отменён | Причина | Снять резерв, вернуть оплату |
| `RETURNED` | Возврат на складе | Строки, состояние товара | См. раздел 8 |

Список статусов WMS и их соответствие каноническим уточняется у партнёра. Статус «Доставлен клиенту» WMS обычно не знает: он приходит от службы доставки и в объём этой интеграции не входит.

```json
{
  "event_id": "wms-evt-77812345",
  "event_type": "order.status_changed",
  "occurred_at": "2026-10-19T08:42:10Z",
  "external_order_id": "SH-1045872",
  "wms_order_id": "WMS-552901",
  "status": "SHIPPED",
  "carrier_code": "CDEK",
  "packages": [
    {"package_id": "1", "tracking_number": "1234567890", "weight_g": 510, "length_mm": 310, "width_mm": 260, "height_mm": 40}
  ],
  "shipped_lines": [
    {"line_id": "1", "sku": "TSH-0042-BLK-M", "qty": 2, "marking_codes": []}
  ]
}
```

**Правила обработки:**

- Идемпотентность по `event_id`: повторно пришедшее событие подтверждается (HTTP 200) и не обрабатывается.
- Статус не откатывается назад. У каждого статуса есть ранг; событие с рангом ниже текущего журналируется и игнорируется.
- `SHIPPED`, `CANCELLED`, `PARTIALLY_SHIPPED` — завершающие для отгрузки; после них допустим только `RETURNED`.
- Если событие пришло раньше, чем магазин получил `ACCEPTED`, IS всё равно применяет его: `wms_order_id` берётся из события.
- Webhook подтверждается (HTTP 200) сразу после записи в очередь IS, а не после обработки магазином — чтобы WMS не слала повторы из-за медленной обработки.

## 7. Поток 3: остатки (WMS → Shop)

Остатки синхронизируются двумя способами одновременно: изменения приходят в течение 5 минут, а раз в сутки полный снимок исправляет накопившиеся расхождения. Магазин показывает покупателю не остаток WMS как есть, а рассчитанный доступный остаток.

| Режим | Когда | Механизм | Назначение |
| --- | --- | --- | --- |
| Изменения (дельта) | При каждом движении на складе | Webhook; иначе опрос раз в 5 мин изменений с момента прошлого запроса | Актуальность витрины |
| Полный снимок | Ежедневно в 03:00 по времени магазина + по кнопке | Запрос всех SKU постранично | Сверка и исправление расхождений |

```json
{
  "event_id": "wms-stk-99120044",
  "event_type": "stock.changed",
  "as_of": "2026-10-19T08:42:10Z",
  "warehouse_id": "MSK-01",
  "items": [
    {"sku": "TSH-0042-BLK-M", "on_hand": 118, "reserved": 6, "available": 112, "quality": "good"}
  ]
}
```

Поля: `on_hand` — физически на складе; `reserved` — зарезервировано WMS под принятые заказы; `available` — годный товар, свободный от резерва; `quality` — `good`, `defect`, `quarantine` (в продажу идёт только `good`). Остаток передаётся абсолютным значением, а не приращением: потерянное или повторное событие не искажает результат.

**Расчёт остатка на сайте:**

```latex
\text{Остаток на сайте} = \text{Available}_{\text{WMS}} - \text{Заказы, ещё не принятые WMS} - \text{Страховой запас}
```

Вычитаются заказы, которые магазин уже принял, но WMS ещё не зарезервировала (в outbox, в очереди, в повторах). Без этого товар продаётся дважды в окне между заказом и его приёмом складом. Страховой запас настраивается по SKU или категории, по умолчанию 0.

**Правила:**

- Данные с `as_of` старше уже сохранённых по этому SKU не применяются.
- SKU, отсутствующий в полном снимке, обнуляется только если снимок получен целиком (все страницы, итоговое количество совпало). Неполный снимок не применяется вовсе.
- При полном снимке IS формирует отчёт о расхождениях: SKU, было, стало, разница. Расхождение больше 5% по SKU или больше 1% позиций каталога — алерт.
- Если складов у партнёра несколько, остаток хранится в разрезе `warehouse_id`, на сайт выводится сумма.

## 8. Отмена, изменение, возвраты

Отменить или изменить заказ можно только до начала упаковки; после этого заказ уходит клиенту, и вопрос решается возвратом. Точное окно (до `PICKING` или до `PACKED`) подтверждает партнёр.

**Отмена (Shop → WMS):**

1. Оператор или клиент отменяет заказ. Магазин переводит его в «Отмена запрошена» и пишет `order.cancel_requested` в outbox.
2. Если заказ ещё не принят WMS (в очереди или в повторах), IS снимает его из очереди и сразу подтверждает отмену.
3. Иначе IS отправляет запрос отмены в WMS по `wms_order_id`.
4. Ответ `CANCELLED` — заказ отменён. Ответ `TOO_LATE` — магазин получает статус «Отмена невозможна», оператор оформляет возврат после доставки.

**Изменение:**

- Получатель, телефон, адрес, комментарий — метод изменения заказа в WMS, если партнёр его поддерживает, в том же окне, что и отмена.
- Состав заказа (товары, количество) не меняется. Рекомендуемый путь — отмена и новый заказ с новым `external_order_id` (например, `SH-1045872-2`).

**Возвраты и невыкупы (WMS → Shop):**

- Когда возврат принят на склад, WMS присылает событие `RETURNED`: `external_order_id`, `return_id`, причина (`customer_return`, `not_picked_up`, `refused`, `undeliverable`), строки с количеством и состоянием (`good`, `defect`).
- Магазин по событию запускает возврат денег и закрывает заказ. Годный товар возвращается в продажу через поток остатков, отдельного действия не нужно.
- Идемпотентность по `return_id`: один возврат может прийти несколькими событиями, если приёмка шла частями.

## 9. Надёжность и обработка ошибок

Ни одно событие не должно теряться или применяться дважды, а недоступность WMS не должна останавливать приём заказов на сайте. Это обеспечивают outbox, очередь с повторами, идемпотентность и регулярные сверки.

**Гарантия доставки.** Все исходящие события магазина пишутся в outbox в одной транзакции с изменением данных. Отдельный процесс публикует их в очередь IS и помечает отправленными. Семантика — «как минимум один раз»; дубли гасятся идемпотентностью.

**Идемпотентность:**

| Операция | Ключ | Где проверяется |
| --- | --- | --- |
| Создание заказа в WMS | `external_order_id` | WMS (ответ `DUPLICATE`) и IS |
| Отмена заказа | `external_order_id` + тип операции | IS |
| Событие статуса, остатка | `event_id` | IS, журнал обработанных событий хранится 30 дней |
| Возврат | `return_id` + `line_id` | Магазин |

Если WMS не проверяет дубли по `external_order_id`, IS перед повторной отправкой после таймаута запрашивает заказ в WMS по этому номеру. Иначе таймаут на стороне сети создаст два заказа на складе.

**Повторы:**

- Повторяются только временные ошибки: таймаут, обрыв соединения, HTTP 5xx, 429. Ошибки валидации (4xx) не повторяются и сразу уходят в DLQ.
- Интервалы: 30 с, 1, 2, 5, 10, 30 минут, далее каждые 30 минут до 24 часов. Затем — DLQ и алерт.
- 429 и заголовок `Retry-After` соблюдаются; лимит запросов партнёра настраивается в IS.
- Таймауты вызовов WMS: соединение 5 с, ответ 30 с.
- При 5 ошибках подряд IS приостанавливает отправку в WMS на 1 минуту (circuit breaker), события копятся в очереди. Магазин продолжает принимать заказы.

**Порядок.** События одного заказа обрабатываются строго последовательно (партиционирование очереди по `external_order_id`). Отмена не может обогнать создание того же заказа. Между разными заказами порядок не важен.

**DLQ.** У оператора есть экран сообщений в DLQ: заказ, ошибка, текст запроса и ответа, кнопки «Отправить повторно» и «Закрыть без отправки». Каждое действие журналируется с пользователем и временем.

**Сверки:**

- Каждый час: заказы в статусе «Передан на склад» дольше 24 часов без движения — IS запрашивает их статус в WMS и исправляет расхождения.
- Каждый час: заказы в «Готов к отгрузке» без `wms_order_id` дольше 30 минут — алерт.
- Ежедневно: полный снимок остатков (раздел 7) и сверка количества заказов, переданных за сутки, с данными WMS.

## 10. Безопасность

По интеграции передаются персональные данные покупателей, поэтому канал шифруется, обе стороны аутентифицируются, а складу уходит только необходимое для доставки.

- **Транспорт:** только HTTPS, TLS 1.2 и выше. Для файлового обмена — SFTP с ключами.
- **IS → WMS:** способ, который поддерживает партнёр; предпочтительно OAuth 2.0 client credentials, иначе API-ключ. Ключи разные для тестовой и боевой среды.
- **WMS → IS (webhooks):** подпись тела запроса HMAC-SHA256 общим секретом в заголовке, метка времени, отклонение запросов старше 5 минут. Дополнительно — список разрешённых IP партнёра.
- **Секреты** хранятся в хранилище секретов (Vault или аналог), не в коде и не в конфигурационных файлах; ротация раз в 12 месяцев и при смене сотрудников с доступом.
- **Минимизация данных:** WMS получает ФИО, телефон, адрес и состав заказа. Данные оплаты, история заказов, дата рождения не передаются.
- **Логи:** телефон, email, ФИО и адрес маскируются (`+7900***4567`). Полные тела запросов хранятся в защищённом журнале с доступом по ролям.
- **Правовая база:** передача персональных данных партнёру оформляется договором (поручение на обработку / DPA) по применимому законодательству — 152-ФЗ или GDPR в зависимости от юрисдикции магазина.

## 11. Мониторинг и журналирование

О любой проблеме интеграции команда должна узнать из алерта раньше, чем от покупателя или склада. Пороги ниже — стартовые; уточняются после месяца эксплуатации.

| Метрика | Порог алерта | Получатель |
| --- | --- | --- |
| Возраст самого старого неотправленного заказа | > 15 мин | Дежурный разработчик |
| Доля ошибок вызовов WMS за 10 мин | > 5% | Дежурный разработчик |
| Сообщений в DLQ | > 0 новых | Оператор, ответственный за заказы |
| Заказы без `ACCEPTED` дольше 30 мин | > 0 | Оператор |
| Заказы «Передан на склад» без движения | > 24 ч | Оператор, менеджер по логистике |
| Время с последнего события остатков | > 1 ч в рабочее время склада | Дежурный разработчик |
| Полный снимок остатков не получен | к 06:00 | Дежурный разработчик |
| Расхождение остатков в снимке | > 1% позиций | Менеджер по логистике |
| Circuit breaker открыт | > 5 мин | Дежурный разработчик |

**Журнал:**

- Каждое сообщение получает `correlation_id`; для заказов это `external_order_id`. По нему видна вся история: событие магазина, запрос в WMS, ответ, повторы, статусы.
- В журнале: время, направление, тип операции, HTTP-статус, длительность, номер попытки, тело запроса и ответа (с маскированием).
- Срок хранения журнала — 90 дней, агрегированных метрик — 1 год.
- Карточка заказа в админке магазина показывает историю обмена со складом.

## 12. Нефункциональные требования

Значения ниже — предлагаемые целевые; объёмы заполняются по данным магазина, лимиты сверяются с возможностями партнёра.

| Требование | Целевое значение |
| --- | --- |
| Заказ принят WMS после перехода в «Готов к отгрузке» | ≤ 2 мин (p95) |
| Статус WMS отражён в магазине | ≤ 5 мин (p95) |
| Изменение остатка отражено на сайте | ≤ 5 мин (p95) |
| Полная сверка остатков | 1 раз в сутки, завершается до 06:00 |
| Пиковая нагрузка | 3× от максимального часа за последний год (распродажи); текущий пик — уточнить |
| Буфер при недоступности WMS | Очередь хранит заказы ≥ 72 ч без потерь |
| Доступность IS | 99,5% в месяц |
| Восстановление после сбоя IS | Без потери событий; RPO = 0 за счёт outbox, RTO ≤ 1 ч |
| Масштабирование | Горизонтальное: несколько экземпляров IS, порядок внутри заказа сохраняется |
| Версионирование | Поле `schema_version` в каждом сообщении; новые необязательные поля не ломают потребителей |

## 13. Тестирование и приёмка

Интеграция принимается, когда все сценарии ниже пройдены на тестовом контуре партнёра, а пилот в бою прошёл без потерянных заказов. Каждый сценарий проверяется автотестом против тестовой среды WMS или её заглушки, построенной по документации партнёра.

**Сценарии приёмки:**

- [ ] Новый товар появляется в WMS до первого заказа с ним; заказ с несинхронизированным SKU ждёт, а не падает.
- [ ] Заказ передаётся и получает `wms_order_id` за ≤ 2 мин.
- [ ] Повторная отправка того же заказа (в том числе после таймаута) не создаёт дубль в WMS.
- [ ] Ошибка валидации (адрес, неизвестный SKU) — заказ в DLQ, оператор исправляет и отправляет повторно.
- [ ] WMS недоступна 1 час: заказы копятся, после восстановления уходят без потерь и дублей, сайт работает.
- [ ] Полный жизненный цикл статусов до `SHIPPED` с трек-номером; клиент получает уведомление.
- [ ] Событие со статусом «ниже» текущего игнорируется; повторное событие не обрабатывается дважды.
- [ ] Частичная отгрузка корректно отражается в заказе и запускает частичный возврат денег.
- [ ] Отмена до сборки проходит; отмена после упаковки получает «Отмена невозможна».
- [ ] Отмена заказа, который ещё в очереди, не доходит до WMS.
- [ ] Возврат и невыкуп закрывают заказ и запускают возврат денег; годный товар возвращается в остаток.
- [ ] Дельта остатков отражается на сайте за ≤ 5 мин; устаревшее событие не перетирает свежие данные.
- [ ] Неполный полный снимок остатков не применяется; полный снимок формирует отчёт о расхождениях.
- [ ] Webhook с неверной подписью или старой меткой времени отклоняется.
- [ ] Нагрузочный тест на 3× пиковый час проходит в пределах целевых задержек.
- [ ] Все алерты из раздела 11 срабатывают на искусственно созданных ситуациях.

**Запуск:**

1. Начальная выгрузка каталога и сверка остатков с партнёром до расхождения 0.
2. Пилот: 10% заказов или одна категория товаров, 1–2 недели, ежедневная ручная сверка с отчётами склада.
3. Полный перевод при отсутствии потерянных и задвоенных заказов в пилоте.
4. План отката: флаг выключения интеграции, заказы снова передаются прежним (ручным) способом.

## 14. Допущения и открытые вопросы

Спецификация опирается на допущения ниже; ответы на вопросы определяют дизайн адаптера и сроки, поэтому их нужно закрыть до начала разработки.

**Допущения:**

- Партнёр предоставляет API (REST или SOAP) и тестовую среду. Если обмен только файлами (CSV/XML по SFTP), меняется адаптер и задержки, а канонический формат остаётся.
- Партнёр сам передаёт груз в службы доставки и печатает этикетки.
- Склад один; несколько складов поддерживаются через `warehouse_id`.

**Вопросы партнёру:**

- [ ] Протокол и документация API, тестовая среда, доступы.
- [ ] Поддерживает ли WMS webhooks для статусов и остатков? Если нет — допустимая частота опроса.
- [ ] Лимиты запросов (в секунду, в минуту), окна технических работ.
- [ ] Проверяет ли WMS дубли по внешнему номеру заказа?
- [ ] Полный список статусов заказа и их коды; есть ли частичная отгрузка.
- [ ] Коды ошибок при создании заказа и их значения.
- [ ] До какого статуса возможны отмена и изменение заказа? Есть ли метод изменения?
- [ ] Справочник служб доставки и пунктов выдачи: кто ведёт, как передаётся.
- [ ] Как WMS считает резерв и `available`; передаётся ли брак и карантин отдельно.
- [ ] Поддержка маркировки, серийных номеров, сроков годности.
- [ ] Время отсечки (cut-off): до какого часа заказ отгружается в тот же день.
- [ ] Формат событий о возвратах и невыкупах.
- [ ] Способ аутентификации и подписи webhooks.

**Вопросы бизнесу:**

- [ ] Какое событие переводит заказ в «Готов к отгрузке»: оплата, подтверждение оператором, другое?
- [ ] Политика при недостаче: отгружать частично или ждать / отменять?
- [ ] Нужен ли страховой запас и какой (по SKU, по категориям)?
- [ ] Кто разбирает DLQ и ошибки передачи: роль, график, время реакции.
- [ ] Входит ли приёмка поставок (ASN) в первый этап?
- [ ] Текущие и ожидаемые объёмы: заказов в сутки, в пиковый час; SKU в каталоге.
