# Спецификация интеграции: интернет-магазин ↔ WMS логистического партнёра

Oct 18, 2026

## 1. Цели и границы

Интеграция автоматически передаёт оплаченные заказы из магазина в WMS партнёра и возвращает в магазин статусы отгрузки, трек-номера и остатки. Реализуется отдельным интеграционным сервисом на нашей стороне с адаптером под API WMS — так платформа магазина не зависит от протокола партнёра.

**Входит в объём:**

- Синхронизация справочника товаров (SKU) из магазина в WMS.
- Передача заказов на отгрузку и их отмена.
- Получение статусов обработки заказа на складе и трек-номера перевозчика.
- Синхронизация остатков из WMS в магазин.
- Получение факта приёмки клиентских возвратов на склад.

**Не входит (кандидаты на следующие этапы):**

- Поставки товара на склад (уведомления о поставке, ASN) и акты приёмки.
- Статусы доставки после передачи посылки перевозчику — их даёт интеграция с перевозчиком.
- Финансовые взаиморасчёты с партнёром и тарификация услуг склада.

**Принципы владения данными:**

| Данные | Мастер-система | Направление |
| --- | --- | --- |
| Справочник товаров | Магазин | Магазин → WMS |
| Заказ (состав, получатель, оплата) | Магазин | Магазин → WMS |
| Факт сборки и отгрузки | WMS | WMS → магазин |
| Физические остатки | WMS | WMS → магазин |
| Остаток, доступный к продаже | Магазин (рассчитывает) | — |

**Допущения (подтвердить с партнёром, см. раздел 15):** WMS предоставляет HTTP API (REST/JSON) и умеет отправлять webhook-уведомления; товар хранится на одном складе; артикул магазина используется как SKU в WMS без перекодировки.

## 2. Глоссарий

| Термин | Значение |
| --- | --- |
| Магазин | Собственная платформа интернет-магазина, мастер-система заказов и каталога |
| WMS | Система управления складом логистического партнёра |
| Интеграционный сервис (ИС) | Сервис на нашей стороне: очереди, адаптер к WMS, журнал сообщений |
| SKU | Артикул товара, единый ключ товара в обеих системах |
| external\_order\_id | Идентификатор заказа в магазине, передаётся в WMS как внешний ключ |
| wms\_order\_id | Идентификатор заказа, присвоенный WMS |
| Свободный остаток | Количество на складе за вычетом резервов и заблокированного товара (брак, карантин) |
| Заказы в пути | Заказы, созданные в магазине, но ещё не принятые WMS (их резерв WMS пока не видит) |
| Outbox | Таблица исходящих событий в БД магазина, пишется в одной транзакции с изменением заказа |
| DLQ | Очередь «мёртвых» сообщений, исчерпавших попытки повтора |
| Идемпотентность | Повторная обработка того же сообщения не меняет результат |

## 3. Участники и архитектура

Магазин и WMS не вызывают друг друга напрямую: весь обмен идёт через интеграционный сервис (ИС), который хранит очередь, журнал и знает протокол партнёра. Смена WMS или изменение её API затрагивает только адаптер.

&#91;embedded content: архитектура интеграции · 3 системы, 2 направления потока\]

Магазин пишет события в outbox, ИС доставляет их в WMS через адаптер с повторами. Обратно WMS отправляет webhook, ИС проверяет и дедуплицирует их и обновляет статусы и остатки в магазине. Если webhook недоступны, планировщик ИС опрашивает API WMS по расписанию (разделы 7 и 8).

| Канал | Направление | Технология |
| --- | --- | --- |
| Товары, заказы, отмены | ИС → WMS | HTTPS-вызовы API WMS, JSON |
| Статусы, остатки, возвраты | WMS → ИС | Webhook (HTTPS POST, JSON); резерв — опрос API |
| Полный снимок остатков | WMS → ИС | Запрос раз в сутки; при отсутствии метода — файл по SFTP |
| Магазин ↔ ИС | внутри контура | Outbox в БД магазина и внутренний API платформы |

ИС разворачивается как отдельный сервис со своей БД (журнал, состояние повторов, связь `external_order_id` ↔ `wms_order_id`).

## 4. Жизненный цикл заказа

Заказ создаётся и оплачивается в магазине, дальше его статус меняют только события WMS и действия оператора. После «Отгружен» статусы доставки приходят от перевозчика и в эту спецификацию не входят.

Отмена возможна из статусов «Передан на склад» и «Собирается»; если WMS отказала, заказ возвращается к последнему складскому статусу (раздел 9). REJECTED может прийти на любом шаге сборки, PARTIALLY\_SHIPPED — вместо SHIPPED (раздел 7).

## 5. Поток 0: справочник товаров

Товар должен существовать в WMS до первого заказа с ним: иначе склад не сможет принять ни поставку, ни заказ. Магазин — мастер справочника, ИС выгружает создание и изменение товаров в WMS.

**Триггеры:** создание товара, изменение любого поля из таблицы ниже, первичная загрузка всего каталога при запуске.

**Операция:** upsert по SKU (создать или обновить). Удаление товаров в WMS не выполняется — товар помечается неактивным (`is_active = false`), так как по нему могут быть остатки и история.

| Поле | Тип | Обяз. | Описание |
| --- | --- | --- | --- |
| sku | string(64) | да | Артикул, ключ |
| name | string(255) | да | Наименование для складских документов |
| barcodes | string\[\] | да | Штрихкоды EAN-13 / Code128, минимум один |
| weight\_g | integer | да | Вес брутто, граммы |
| length\_mm, width\_mm, height\_mm | integer | да | Габариты в упаковке, миллиметры |
| declared\_value | decimal(12,2) | да | Оценочная стоимость для страхования, валюта магазина |
| vat\_rate | string | нет | Ставка НДС, если WMS печатает документы для покупателя |
| is\_marked | boolean | нет | Подлежит обязательной маркировке (сканирование кодов при сборке) |
| shelf\_life\_days | integer | нет | Срок годности, если товар учитывается по партиям |
| is\_active | boolean | да | Активен ли товар |

**Правила:**

1. Заказ, содержащий SKU, не подтверждённый WMS, не отправляется: ИС ставит его в ожидание и повторяет после синхронизации товара.
2. Изменение штрихкода или габаритов отправляется сразу — от них зависит приёмка и выбор упаковки на складе.
3. Ответ WMS с ошибкой валидации товара — алерт контент-менеджеру, а не повтор.

## 6. Поток 1: передача заказа на склад

Заказ уходит в WMS, как только он оплачен (или подтверждён оператором при оплате при получении). Передача асинхронная: магазин пишет событие в outbox, ИС доставляет его в WMS с повторами.

**Триггер:** переход заказа в статус «Оплачен» или «Подтверждён (наложенный платёж)». Событие `order.ready_for_fulfillment` пишется в outbox в той же транзакции, что и смена статуса.

**Последовательность:**

1. ИС читает событие из outbox и загружает актуальный заказ из магазина.
2. ИС валидирует заказ (правила ниже) и преобразует в формат WMS.
3. ИС вызывает метод создания заказа WMS с ключом идемпотентности `external_order_id`.
4. При успехе ИС сохраняет `wms_order_id` и переводит заказ в магазине в статус «Передан на склад».
5. При ошибке — повтор или ручной разбор по правилам раздела 10.

**Модель заказа (канонический формат ИС):**

| Поле | Тип | Обяз. | Описание |
| --- | --- | --- | --- |
| external\_order\_id | string(64) | да | ID заказа в магазине, ключ идемпотентности |
| order\_number | string(32) | да | Номер заказа для покупателя, печатается на документах |
| created\_at | datetime ISO 8601 с TZ | да | Дата создания заказа |
| priority | enum: normal, express | да | Приоритет сборки |
| ship\_by\_date | date | нет | Крайняя дата отгрузки |
| delivery.carrier\_code | string | да | Код службы доставки по справочнику WMS |
| delivery.service\_type | enum: courier, pickup\_point, post | да | Способ доставки |
| delivery.pickup\_point\_id | string | условно | Обязателен для pickup\_point |
| recipient.full\_name | string(255) | да | ФИО получателя |
| recipient.phone | string E.164 | да | Телефон, формат +79991234567 |
| recipient.email | string | нет | Email получателя |
| address.\* | object | условно | Страна, индекс, регион, город, улица, дом, квартира; обязателен для courier и post |
| items\[\].line\_id | string | да | ID строки заказа, нужен для частичной отгрузки |
| items\[\].sku | string | да | Артикул |
| items\[\].quantity | integer > 0 | да | Количество |
| items\[\].unit\_price | decimal(12,2) | да | Цена за единицу с учётом скидок |
| payment.type | enum: prepaid, cod | да | Предоплата или наложенный платёж |
| payment.cod\_amount | decimal(12,2) | условно | Сумма к получению с покупателя, обязательна для cod |
| declared\_value | decimal(12,2) | да | Объявленная ценность отправления |
| comment | string(500) | нет | Комментарий для склада (подарочная упаковка, вложение) |

**Пример запроса:**

```json
{
  "external_order_id": "ord_8f3a21",
  "order_number": "100245",
  "created_at": "2026-10-18T14:05:12+05:00",
  "priority": "normal",
  "delivery": { "carrier_code": "CDEK", "service_type": "pickup_point", "pickup_point_id": "EKB123" },
  "recipient": { "full_name": "Иванова Анна Сергеевна", "phone": "+79991234567" },
  "items": [
    { "line_id": "1", "sku": "TSH-BLK-M", "quantity": 2, "unit_price": 1490.00 }
  ],
  "payment": { "type": "prepaid" },
  "declared_value": 2980.00
}
```

**Валидации до отправки:**

1. Все SKU существуют в WMS (поток 0) и активны.
2. Для `cod` сумма `cod_amount` равна сумме заказа к оплате.
3. Адрес или пункт выдачи заполнены по выбранному способу доставки.
4. Телефон в формате E.164.

**Обработка ответа WMS:**

| Ответ | Действие ИС | Статус в магазине |
| --- | --- | --- |
| Успех, получен wms\_order\_id | Сохранить связь заказов | Передан на склад |
| Дубликат (заказ с этим external\_order\_id уже есть) | Считать успехом, запросить wms\_order\_id | Передан на склад |
| Ошибка валидации (4xx) | Без повтора, алерт оператору | Ошибка передачи на склад |
| Таймаут, 5xx, 429 | Повтор по расписанию раздела 10 | Без изменений |
| Недостаточно остатка (если WMS резервирует при создании) | Без повтора, алерт оператору | Требует внимания |

Изменение состава или адреса после передачи — по правилам раздела 9.

## 7. Поток 2: статусы отгрузки

WMS сообщает о каждой смене статуса заказа webhook-событием; ИС переводит статус WMS в статус магазина по таблице ниже и сохраняет трек-номер. Если партнёр не поддерживает webhook, ИС опрашивает WMS каждые 5 минут по заказам в незавершённых статусах.

**Маппинг статусов** (коды WMS условные, заменить на фактические после получения документации партнёра):

| Статус WMS | Смысл | Статус в магазине | Уведомить покупателя |
| --- | --- | --- | --- |
| ACCEPTED | Заказ принят складом | Передан на склад | нет |
| PICKING | Идёт сборка | Собирается | нет |
| PACKED | Собран и упакован | Собран | нет |
| SHIPPED | Передан перевозчику, есть трек-номер | Отгружен | да, с трек-номером |
| PARTIALLY\_SHIPPED | Отгружена часть позиций | Требует внимания | после решения оператора |
| CANCELLED | Отменён по нашему запросу | Отменён | по сценарию отмены |
| REJECTED | Склад не может выполнить (нет товара, брак) | Требует внимания | после решения оператора |
| Неизвестный код | — | Без изменений, алерт | нет |

**Модель события:**

| Поле | Тип | Обяз. | Описание |
| --- | --- | --- | --- |
| event\_id | string | да | Уникальный ID события, ключ дедупликации |
| external\_order\_id | string | да | ID заказа магазина |
| wms\_order\_id | string | да | ID заказа в WMS |
| status | string | да | Код статуса WMS |
| occurred\_at | datetime ISO 8601 с TZ | да | Время события на складе |
| reason\_code, reason\_text | string | нет | Причина для REJECTED и PARTIALLY\_SHIPPED |
| carrier\_code, tracking\_number | string | для SHIPPED | Перевозчик и трек-номер |
| packages\[\] | object | нет | Места: вес, габариты, номер места |
| shipped\_items\[\] | object | для SHIPPED | line\_id, sku, quantity, коды маркировки при наличии |

**Правила обработки:**

1. Дубликат по `event_id` игнорируется, ответ 200.
2. Событие с `occurred_at` раньше последнего применённого не меняет статус, но сохраняется в журнале (защита от перестановки событий).
3. Статусы движутся только вперёд по цепочке ACCEPTED → PICKING → PACKED → SHIPPED; откат назад — алерт.
4. При SHIPPED магазин сохраняет фактически отгруженные позиции; расхождение с заказом — статус «Требует внимания».
5. Дальнейшее отслеживание доставки идёт по трек-номеру через интеграцию с перевозчиком, вне этой спецификации.

## 8. Поток 3: синхронизация остатков

WMS — мастер физических остатков, а остаток к продаже рассчитывает магазин. Используются два режима: оперативные изменения (дельта) и ежедневный полный снимок для сверки.

**Расчёт остатка к продаже:**

```latex
\text{К продаже} = \max\left(0,\ \text{Свободный остаток WMS} - \text{Заказы в пути} - \text{Страховой запас}\right)
```

«Заказы в пути» — количество по SKU в заказах магазина, которые оплачены, но ещё не получили ответ ACCEPTED от WMS. Без этой поправки товар продаётся повторно в окне между оплатой и резервом на складе. Страховой запас задаётся в магазине на уровне SKU или категории, по умолчанию 0.

**Режимы:**

| Режим | Источник | Частота | Назначение |
| --- | --- | --- | --- |
| Дельта | Webhook WMS об изменении остатка, иначе опрос изменённых с момента последнего запроса | Событие или каждые 5 минут | Оперативное обновление витрины |
| Полный снимок | Выгрузка всех SKU из WMS | Ежедневно в 03:00 по времени магазина | Сверка и исправление расхождений |

**Модель записи остатка:**

| Поле | Тип | Обяз. | Описание |
| --- | --- | --- | --- |
| sku | string | да | Артикул |
| warehouse\_id | string | да | Код склада (на будущее, при нескольких складах) |
| on\_hand | integer | да | Физически на складе |
| reserved | integer | да | В резерве под принятые заказы |
| blocked | integer | да | Брак, карантин, недоступен к отгрузке |
| available | integer | да | Свободный остаток: on\_hand − reserved − blocked |
| snapshot\_at | datetime ISO 8601 с TZ | да | Момент, на который зафиксирован остаток |

**Правила:**

1. Запись применяется, только если `snapshot_at` новее последней применённой по этому SKU.
2. ИС сохраняет абсолютные значения, а не приращения: потеря одного события исправляется следующим.
3. SKU, отсутствующий в полном снимке, обнуляется, только если снимок помечен WMS как полный и успешно загружен целиком.
4. Расхождение снимка с текущим значением в магазине больше 5% по SKU попадает в отчёт сверки (раздел 12).
5. Неизвестный магазину SKU — запись в журнал, без ошибки.

## 9. Изменения, отмены и возвраты

После передачи на склад заказ нельзя молча изменить в магазине: любое изменение идёт запросом в WMS, а WMS вправе отказать, если сборка уже зашла далеко.

**Отмена заказа:**

1. Покупатель или оператор отменяет заказ в магазине; заказ получает промежуточный статус «Отмена запрошена».
2. ИС отправляет запрос отмены в WMS по `wms_order_id`.
3. WMS подтвердила отмену → статус «Отменён», запускается возврат денег, остаток вернётся через поток 3.
4. WMS отказала (заказ уже PACKED или SHIPPED) → статус возвращается к последнему складскому, оператор получает задачу; после отгрузки отмена оформляется как возврат.
5. Заказ ещё не передан в WMS → отмена выполняется в магазине, событие из outbox снимается.

До какого статуса склад принимает отмену, фиксируется в договоре с партнёром (раздел 15); по умолчанию — до PACKED.

**Изменение заказа:**

| Изменение | До передачи в WMS | После передачи |
| --- | --- | --- |
| Адрес, получатель, телефон | Свободно | Метод обновления WMS, если есть; иначе отмена и повторная передача |
| Состав заказа | Свободно | Только отмена и новый заказ |
| Способ доставки | Свободно | Отмена и повторная передача |

При пересоздании новый заказ получает новый `external_order_id` с суффиксом версии (`ord_8f3a21-v2`), чтобы не сработала защита от дубликатов.

**Частичная отгрузка и недостача:** при PARTIALLY\_SHIPPED или REJECTED оператор выбирает: дозаказать позицию, отменить недостающие строки с частичным возвратом денег или отменить заказ целиком.

**Возвраты от покупателей:** WMS отправляет событие `return.received` при приёмке возврата на складе.

| Поле | Описание |
| --- | --- |
| external\_order\_id | Заказ, по которому возврат |
| return\_id | ID возврата в WMS |
| items\[\].sku, quantity | Принятые позиции |
| items\[\].condition | sellable (годен к продаже) или defective (брак) |
| received\_at | Время приёмки |

Магазин закрывает заявку на возврат и запускает возврат денег; годный товар появится в свободном остатке через поток 3, брак уйдёт в `blocked`.

## 10. Надёжность и обработка ошибок

Доставка сообщений — «как минимум один раз» с идемпотентной обработкой на обеих сторонах: ни один заказ не теряется и ни один не создаётся на складе дважды.

**Исходящие вызовы (ИС → WMS):**

1. События берутся из outbox, а не отправляются из кода бизнес-логики напрямую — заказ не потеряется при падении сервиса между коммитом и вызовом.
2. Ключ идемпотентности: `external_order_id` для заказов, `sku` для товаров, `external_order_id + действие` для отмен. Если WMS поддерживает заголовок `Idempotency-Key`, ИС передаёт его.
3. Сообщения по одному заказу обрабатываются строго последовательно (партиционирование очереди по `external_order_id`): отмена не обгонит создание.
4. Таймаут вызова — 10 секунд на соединение и 30 секунд на ответ.

**Расписание повторов:** 1 мин → 5 мин → 15 мин → 1 ч → далее каждый час до 24 часов с момента первой попытки. После этого сообщение уходит в DLQ, заказ получает статус «Ошибка передачи на склад», срабатывает алерт.

**Классификация ошибок:**

| Ошибка | Повтор | Действие |
| --- | --- | --- |
| Сетевая ошибка, таймаут | да | По расписанию |
| HTTP 5xx | да | По расписанию |
| HTTP 429 | да | Ждать время из `Retry-After`, иначе по расписанию |
| HTTP 401, 403 | нет | Критичный алерт: проблема учётных данных, очередь приостанавливается |
| HTTP 400, 422 | нет | В DLQ, задача оператору с текстом ошибки WMS |
| HTTP 409 (дубликат) | нет | Считать успехом, запросить состояние заказа в WMS |

**Входящие webhook (WMS → ИС):**

1. ИС проверяет подпись, сохраняет событие в журнал и отвечает 200 за время до 3 секунд; обработка — асинхронно.
2. Дубликат по `event_id` — сразу 200 без обработки.
3. Ответ не-2xx означает для WMS «повторить»; ИС отвечает 5xx только если не смогла сохранить событие.

**Внутренние коды ошибок ИС** (для журнала и экранов оператора):

| Код | Значение |
| --- | --- |
| INT-001 | SKU не найден в WMS |
| INT-002 | Ошибка валидации заказа до отправки |
| INT-003 | WMS отклонила заказ (ошибка валидации) |
| INT-004 | Исчерпаны повторы, сообщение в DLQ |
| INT-005 | Неизвестный статус WMS |
| INT-006 | Недопустимый переход статуса |
| INT-007 | Неверная подпись webhook |
| INT-008 | Ошибка аутентификации в WMS |

## 11. Безопасность

Весь обмен идёт по HTTPS, обе стороны аутентифицируют друг друга, а персональные данные покупателей передаются в минимально нужном объёме и не попадают в логи открытым текстом.

| Область | Требование |
| --- | --- |
| Транспорт | HTTPS, TLS 1.2 и выше, проверка сертификата партнёра |
| ИС → WMS | Способ, который поддерживает WMS: OAuth 2.0 client credentials (предпочтительно) или API-ключ в заголовке |
| WMS → ИС (webhook) | Подпись тела HMAC-SHA256 общим секретом в заголовке + метка времени; запросы старше 5 минут отклоняются |
| Сетевой доступ | Список разрешённых IP-адресов WMS для webhook-эндпоинта |
| Секреты | В хранилище секретов, не в коде и конфигах; ротация раз в 12 месяцев и при компрометации без простоя (два активных ключа) |
| Персональные данные | В WMS передаются только ФИО, телефон, адрес, email — то, что нужно для доставки; договор с партнёром включает поручение на обработку ПДн по применимому законодательству |
| Логи | Телефон, email и адрес маскируются (`+7999*****67`); полные тела сообщений хранятся в журнале ИС с ограниченным доступом |
| Права | Отдельная техническая учётная запись ИС в WMS с доступом только к нужным методам |

## 12. Мониторинг, логирование и сверки

Каждое сообщение прослеживается от заказа в магазине до ответа WMS, а зависшие заказы и расхождения остатков обнаруживаются автоматически, а не по жалобам покупателей.

**Журнал сообщений ИС:** направление, тип, `external_order_id`, `wms_order_id`, `correlation_id`, тело запроса и ответа (с маскированием), HTTP-код, число попыток, время. Хранение — 90 дней.

**Алерты:**

| Условие | Порог | Получатель |
| --- | --- | --- |
| Оплаченный заказ не принят WMS | более 15 минут | Дежурный разработчик |
| Принятый заказ не отгружен | дольше SLA склада (уточнить, раздел 15) | Операционный менеджер |
| DLQ не пуста | 1 сообщение | Дежурный разработчик |
| Ошибки 401/403 от WMS | 1 ошибка | Дежурный разработчик, критично |
| Доля ошибочных вызовов WMS | более 5% за 15 минут | Дежурный разработчик |
| Нет обновлений остатков | более 30 минут в рабочее время склада | Дежурный разработчик |
| Неверная подпись webhook | 3 за 10 минут | Безопасность |

**Ежедневные сверки (после полного снимка остатков):**

1. Заказы: все заказы магазина в статусах от «Передан на склад» до «Отгружен» за 7 дней сравниваются со статусами в WMS; расхождения — в отчёт.
2. Остатки: SKU с расхождением более 5% между магазином и снимком WMS.
3. Справочник: SKU активные в магазине, но отсутствующие в WMS.

**Инструменты оператора:** экран заказов с ошибками интеграции, просмотр журнала по заказу, ручная повторная отправка, принудительный запрос статуса и остатков из WMS.

## 13. Нефункциональные требования

Целевые значения ниже — предложение для согласования с бизнесом и партнёром; фактические объёмы заказов нужно получить до финализации (раздел 15).

| Параметр | Целевое значение |
| --- | --- |
| Задержка передачи заказа в WMS после оплаты | не более 2 минут для 95% заказов |
| Задержка обновления статуса в магазине после события WMS | не более 5 минут |
| Задержка обновления остатка на витрине | не более 5 минут (webhook), не более 15 минут (опрос) |
| Доступность ИС | 99,5% в месяц |
| Пропускная способность | 3-кратный запас к пиковому часу распродаж |
| Работа при недоступности WMS | Заказы копятся в очереди до 24 часов без потерь, приём заказов в магазине не блокируется |
| Хранение журнала сообщений | 90 дней |
| Масштабирование | Поддержка нескольких складов через `warehouse_id` без изменения контракта |

## 14. Тестирование и приёмка

Интеграция принимается после прохождения всех сценариев ниже на тестовом контуре WMS и двух недель пилота на реальных заказах с ежедневной сверкой без неразобранных расхождений.

**Контуры:** тестовый стенд WMS партнёра (песочница) с отдельными учётными данными; мок WMS на нашей стороне для автотестов и нагрузочного теста.

| № | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| 1 | Создание и изменение товара | Товар появился и обновился в WMS |
| 2 | Оплаченный заказ с предоплатой | Принят WMS, статус «Передан на склад» не позже 2 минут |
| 3 | Заказ с наложенным платежом | В WMS передана верная сумма к получению |
| 4 | Повторная отправка того же заказа | Дубликат в WMS не создан |
| 5 | Заказ с SKU, которого нет в WMS | Заказ не отправлен, ошибка INT-001, после синхронизации товара уходит сам |
| 6 | Полный цикл статусов до SHIPPED | Статусы и трек-номер в магазине, покупатель уведомлён |
| 7 | События статусов пришли в обратном порядке | Итоговый статус верный |
| 8 | Отмена до сборки и после упаковки | В первом случае «Отменён», во втором отказ и задача оператору |
| 9 | Частичная отгрузка | Статус «Требует внимания», фактические позиции сохранены |
| 10 | Изменение остатка и полный снимок | Остаток к продаже пересчитан по формуле раздела 8 |
| 11 | WMS недоступна 2 часа | Заказы накоплены и доставлены после восстановления без потерь |
| 12 | Webhook с неверной подписью | Отклонён, алерт |
| 13 | Возврат принят складом (годен и брак) | Возврат закрыт, остатки обновлены корректно |
| 14 | Нагрузка: 3-кратный пиковый час | Задержки в пределах раздела 13 |
