## Назначение и границы

Интеграция автоматически передаёт оплаченные заказы из магазина в WMS партнёра и возвращает в магазин статусы отгрузки и остатки. Цель — исключить ручной перенос заказов, не продавать отсутствующий товар и показывать покупателю актуальный статус.

**В границах проекта:** синхронизация справочника товаров, передача заказа, отмена заказа, статусы отгрузки с трек-номером, остатки (изменения и ежедневная сверка), уведомление о принятом возврате.

**Вне границ:** поставки товара на склад (ASN), взаиморасчёты и биллинг склада, расчёт стоимости доставки, интеграция со службами доставки напрямую. Каждый пункт может быть включён после ответов на вопросы З9 и П14.

| Термин | Значение |
| --- | --- |
| Магазин | Собственная платформа интернет-магазина, мастер-система заказов и товаров |
| WMS | Система управления складом логистического партнёра |
| Интеграционный сервис | Промежуточный сервис на стороне магазина, который преобразует и доставляет сообщения |
| SKU | Артикул товара магазина, основной ключ товара в обмене |
| Свободный остаток | Количество, которое WMS может отгрузить: физический остаток минус резервы и брак |
| Доступно к продаже | Остаток на сайте: свободный остаток минус заказы, ещё не принятые WMS |
| Событие | Сообщение об изменении (статус, остаток) с уникальным идентификатором и временем возникновения |

## Архитектура обмена

Магазин не обращается к WMS напрямую: все вызовы идут через отдельный интеграционный сервис, который хранит журнал, повторяет неудачные отправки и изолирует магазин от формата партнёра.

&#91;embedded content: архитектура обмена · 3 системы, 4 компонента сервиса\]

Заказы идут слева направо через outbox и адаптер; события WMS возвращаются справа налево через приёмник вебхуков во внутренний API магазина.

- Магазин → WMS: асинхронно, через outbox и очередь внутри сервиса; оформление заказа не зависит от доступности WMS.
- WMS → магазин: вебхуки (или опрос по расписанию), приёмник сначала сохраняет событие и отвечает 200, затем обрабатывает.
- Интеграционный сервис владеет таблицами соответствия идентификаторов, журналом обмена и DLQ.
- Замена партнёра или добавление склада требует нового адаптера, магазин не меняется.

## Поток 0. Справочник товаров

Товар должен существовать в WMS раньше, чем в неё придёт заказ с этим SKU; поэтому справочник синхронизируется первым и при каждом изменении карточки.

**Направление:** магазин → WMS. **Триггер:** создание или изменение в магазине любого поля из таблицы ниже. **Первичная загрузка:** пакетная выгрузка всех активных SKU перед запуском.

| Поле | Тип | Обяз. | Описание |
| --- | --- | --- | --- |
| sku | string(64) | да | Артикул магазина, ключ товара |
| name | string(255) | да | Наименование для сборщика |
| barcodes | string\[\] | да | Штрихкоды EAN-13 или внутренние; минимум один |
| weight\_g | integer | да | Вес брутто, граммы |
| length\_mm, width\_mm, height\_mm | integer | да | Габариты в упаковке, миллиметры |
| vat\_rate | string | нет | Ставка НДС, если склад печатает документы |
| is\_kit, components\[\] | boolean, массив {sku, qty} | нет | Комплект и его состав |
| track\_serial, track\_expiry, track\_marking | boolean | нет | Учитывать серийный номер, срок годности, код маркировки |
| active | boolean | да | Выведенный товар не удаляется, а деактивируется |

**Правила.** Передача идемпотентна: повторная отправка той же карточки обновляет её, а не создаёт дубль. Ошибка валидации в WMS ставит товару признак «не синхронизирован»; заказ с таким SKU не отправляется на склад и попадает в очередь «Проблема» с причиной `SKU_NOT_SYNCED`.

## Поток 1. Передача заказа на склад

Заказ уходит в WMS в течение 2 минут после того, как стал готов к отгрузке, и считается переданным только после подтверждения от WMS.

**Направление:** магазин → WMS. **Триггер:** заказ оплачен (предоплата) или подтверждён оператором (оплата при получении), см. Д4.

1. Магазин в одной транзакции с изменением заказа пишет событие `order.ready_for_fulfillment` в таблицу исходящих сообщений (outbox).
2. Интеграционный сервис забирает событие, проверяет заказ по правилам валидации и преобразует его в формат WMS.
3. Сервис вызывает метод создания заказа в WMS с ключом идемпотентности, равным номеру заказа.
4. Успешный ответ: сервис сохраняет идентификатор заказа в WMS и переводит заказ в статус «Передан на склад».
5. Бизнес-ошибка (неизвестный SKU, неверный адрес): заказ получает статус «Проблема» с кодом и текстом ошибки, оператор получает уведомление, повтора нет.
6. Техническая ошибка (тайм-аут, 5xx, 429): повтор по правилам раздела «Надёжность»; статус в магазине остаётся «Передаётся на склад».

### Правила валидации перед отправкой

- Все SKU заказа синхронизированы со справочником WMS и активны.
- Для курьерской и почтовой доставки заполнены город, улица, дом; для ПВЗ — идентификатор пункта.
- Телефон приводится к E.164; ошибка приведения — бизнес-ошибка `INVALID_PHONE`.
- Сумма строк совпадает с объявленной ценностью, сумма наложенного платежа не больше итога заказа.
- Длины строк обрезаются только там, где это разрешено партнёром; иначе — бизнес-ошибка.

## Поток 2. Статусы отгрузки

WMS сообщает о каждом изменении статуса заказа; магазин применяет только переходы вперёд по своей модели и игнорирует устаревшие события.

**Направление:** WMS → магазин. **Способ:** вебхук `POST /wms/events` в интеграционный сервис; если вебхуков нет — опрос изменённых заказов раз в 5 минут с меткой времени последнего опроса.

&#91;embedded content: статусы заказа в магазине · 10 статусов, 3 конечных\]

Основной путь идёт сверху вниз; из «Проблемы» заказ возвращается в «Передаётся на склад» после исправления, а отмена проходит через промежуточный статус «Отменяется» и возможна, пока WMS её принимает (П9).

### Маппинг статусов

Коды WMS условные и заменяются на реальные после ответа на П7.

| Статус WMS | Статус магазина | Видит покупатель | Данные в событии |
| --- | --- | --- | --- |
| accepted | Передан на склад | Заказ собирается | wms\_order\_id |
| picking | Собирается | Заказ собирается | — |
| shortage | Проблема | Заказ собирается | Строки и количество недостачи |
| packed | Собран | Заказ собран | Число мест, вес |
| shipped | Передан в доставку | Передан в доставку | Трек-номер, служба, коды маркировки и серийные номера |
| delivered | Доставлен | Доставлен | Время вручения, сумма наложенного платежа |
| not\_delivered | Возвращается | Не удалось доставить | Причина |
| returned | Возврат принят | Возврат получен | Строки, состояние товара (годен или брак) |
| cancelled | Отменён | Отменён | Инициатор отмены |

### Правила применения

- Каждое событие несёт `event_id` и `occurred_at`; повторное событие с тем же `event_id` подтверждается ответом 200 и не применяется второй раз.
- Порядок статусов задан рангом; событие с рангом ниже текущего статуса заказа записывается в журнал, но статус не меняет.
- Конечные статусы: «Доставлен», «Возврат принят», «Отменён»; после них меняются только данные возврата.
- Неизвестный статус WMS не ломает обработку: событие сохраняется, уходит алерт, статус заказа не меняется.
- Событие для неизвестного заказа сохраняется в очередь разбора и повторно сопоставляется через 10 минут (заказ мог ещё не сохранить ответ WMS).

## Поток 3. Остатки

Магазин получает от WMS абсолютные значения свободного остатка по SKU, а не приращения: повтор или потеря одного сообщения не накапливает ошибку, а ежедневная полная сверка исправляет расхождения.

**Направление:** WMS → магазин.

| Режим | Когда | Содержание |
| --- | --- | --- |
| Изменения | Вебхук при каждом изменении, либо опрос раз в 5 минут | SKU, свободный остаток, время расчёта в WMS |
| Полная сверка | Ежедневно в 03:00 по времени склада и по кнопке оператора | Все активные SKU склада |

### Расчёт остатка на сайте

```latex
\text{Доступно к продаже} = \text{Свободный остаток WMS} - \text{Заказы, ещё не принятые WMS} - \text{Страховой запас}
```

Заказы, принятые WMS, уже зарезервированы на складе и входят в его свободный остаток, поэтому повторно не вычитаются. Страховой запас по умолчанию 0, настраивается на уровне SKU (вопрос З7). Отрицательное значение показывается как 0.

### Правила применения

- Значение применяется, только если его время расчёта новее последнего сохранённого для этого SKU; более старое значение игнорируется.
- При полной сверке SKU, которого нет в выгрузке, но есть в магазине, получает остаток 0 и попадает в отчёт.
- Расхождение больше 5% SKU между сверкой и текущими данными магазина вызывает алерт: это признак потерянных событий.
- Изменение остатка до 0 и с 0 сразу снимает или возвращает товар в продажу; остальные изменения можно применять пакетом раз в минуту.

## Поток 4. Отмена, изменение, возврат

Отмена заказа в магазине считается выполненной только после подтверждения WMS; до этого заказ находится в статусе «Отменяется» и не освобождает остаток.

### Отмена

1. Покупатель или оператор отменяет заказ; если заказ ещё не передан в WMS, событие создания снимается из очереди и заказ сразу получает статус «Отменён».
2. Если заказ передан, магазин ставит статус «Отменяется» и пишет событие `order.cancel_requested` в outbox.
3. Интеграционный сервис вызывает метод отмены WMS; ответ «отменён» переводит заказ в «Отменён», резерв на складе снимается, новый остаток придёт в потоке 3.
4. Ответ «отмена невозможна» (заказ уже собран или отгружен): статус возвращается к текущему статусу WMS, оператор получает задачу; дальше — перехват у службы доставки или возврат.

### Изменение

В первой версии состав и адрес заказа после передачи в WMS не меняются (Д8). Изменение оформляется как отмена и новый заказ с номером вида `<номер>-2`, чтобы не нарушать уникальность внешнего ключа. Если партнёр поддерживает изменение адреса или интервала до сборки (П9), это добавляется отдельным методом.

### Возврат

WMS присылает событие `returned` с составом и состоянием каждой единицы. Магазин переводит заказ в «Возврат принят» и создаёт задачу на возврат денег по своему регламенту; годный товар возвращается в продажу через поток остатков, бракованный не учитывается.

## Контракт API

Интеграционный сервис скрывает формат WMS от магазина: магазин работает с каноническими сообщениями ниже, а адаптер WMS переводит их в методы партнёра. Пути методов WMS условные до получения документации (П1).

| Направление | Метод и путь | Назначение |
| --- | --- | --- |
| Сервис → WMS | `PUT /products/{sku}` | Создать или обновить карточку товара |
| Сервис → WMS | `POST /orders` + заголовок `Idempotency-Key: {order_id}` | Создать заказ |
| Сервис → WMS | `POST /orders/{order_id}/cancel` | Отменить заказ |
| Сервис → WMS | `GET /orders/changes?since={ts}` | Опрос статусов, если нет вебхуков |
| Сервис → WMS | `GET /stock` и `GET /stock?since={ts}` | Полная выгрузка и изменения остатков |
| WMS → сервис | `POST /wms/events` | Вебхук: статусы, остатки, возвраты |
| Сервис → магазин | `PATCH /internal/orders/{order_id}/fulfillment` | Обновить статус и данные отгрузки |
| Сервис → магазин | `PUT /internal/stock` | Пакет остатков по SKU |
| Магазин → сервис | таблица outbox | События `order.ready_for_fulfillment`, `order.cancel_requested`, `product.changed` |

  "warehouse_code": "MAIN",

## Надёжность и обработка ошибок

Доставка сообщений — «как минимум один раз», а повторы безопасны за счёт идемпотентности на обеих сторонах; ни один заказ не теряется при падении любого компонента.

- **Outbox.** Событие пишется в той же транзакции, что и изменение заказа или товара; отдельный процесс публикует события и отмечает отправленные. Это исключает ситуацию «заказ оплачен, а событие не создано».
- **Идемпотентность исходящих.** Создание заказа — по `order_id`, карточка — по `sku`, отмена повторно безопасна.
- **Идемпотентность входящих.** Таблица обработанных `event_id` хранится не менее 30 дней.
- **Порядок.** События одного заказа обрабатываются последовательно (партиционирование по `order_id`); между разными заказами порядок не важен.
- **Повторы.** Экспоненциальная задержка: 1, 2, 5, 15, 30 минут, далее каждый час до 24 часов; затем сообщение уходит в очередь недоставленных (DLQ) и создаётся алерт.
- **Защита от перегрузки.** Соблюдение лимитов WMS (П2), учёт заголовка `Retry-After` при 429; при 5 подряд отказах WMS запросы приостанавливаются на 1 минуту (circuit breaker).

| Ошибка | Пример | Повтор | Действие |
| --- | --- | --- | --- |
| Сетевая, тайм-аут | Нет ответа за 30 с | да | Повтор; перед повтором создания проверить, не создан ли заказ |
| 5xx от WMS | 502, 503 | да | Повтор по расписанию |
| 429 | Превышен лимит | да | Ждать `Retry-After` |
| 401, 403 | Истёк или отозван ключ | нет | Критический алерт, остановка отправки |
| 4xx бизнес | Неизвестный SKU, неверный адрес | нет | Статус «Проблема», задача оператору |
| 409 дубль | Заказ уже существует | нет | Сверить тело, считать успехом |
| Ошибка в магазине | Внутренний API недоступен | да | Событие WMS остаётся в хранилище и обрабатывается позже |

Оператор может переотправить любое сообщение из DLQ или статуса «Проблема» после исправления данных; переотправка использует тот же ключ идемпотентности.

## Безопасность

Партнёру передаются только данные, нужные для сборки и доставки, по защищённому каналу, а входящие вебхуки принимаются только с проверенной подписью.

- Весь обмен — по HTTPS, TLS 1.2 и выше.
- Ключи доступа к WMS хранятся в менеджере секретов, не в коде и не в конфигурации репозитория; ротация не реже раза в год и сразу при утечке.
- Вебхуки проверяются по подписи HMAC-SHA256 тела с общим секретом и по метке времени (отклонение не больше 5 минут); дополнительно — белый список IP партнёра.
- Персональные данные: в WMS уходят только ФИО, телефон, email и адрес получателя. В логах телефон, email и адрес маскируются.
- Сырые сообщения с персональными данными хранятся 30 дней, затем удаляются или обезличиваются.
- Внутренние методы магазина `/internal/*` доступны только из сети интеграционного сервиса и требуют сервисного токена.

## Мониторинг и сверки

Главный сигнал здоровья интеграции — возраст самого старого непереданного заказа: если он растёт, заказы не уходят на склад, даже когда ошибок в логах нет.

**Журнал обмена.** Каждое сообщение хранится со статусом (новое, отправлено, ошибка, DLQ), числом попыток, телом запроса и ответа, `correlation_id`, общим для всех событий одного заказа. Срок хранения — 30 дней.

**Экран оператора.** Список заказов в статусе «Проблема» и сообщений в DLQ с причиной, фильтры по дате и типу, кнопка «Переотправить», просмотр истории событий заказа.

| Алерт | Порог | Важность | Кому |
| --- | --- | --- | --- |
| Самый старый непереданный заказ | Старше 15 минут | Критично | Дежурный разработчик |
| WMS отвечает 401 или 403 | Первый случай | Критично | Дежурный разработчик |
| Доля ошибок вызовов WMS | Больше 10% за 10 минут | Высокая | Дежурный разработчик |
| Нет вебхуков от WMS | Больше 60 минут в рабочее время склада | Высокая | Дежурный, менеджер партнёра |
| Новые сообщения в DLQ | Любое | Средняя | Поддержка |
| Заказы в статусе «Проблема» | Больше 5 за час | Средняя | Операторы |
| Расхождение при ежедневной сверке остатков | Больше 5% SKU | Средняя | Менеджер склада |
| Заказ без статуса «Передан в доставку» | Через 48 часов после передачи | Низкая | Операторы |

Получатели алертов уточняются по вопросу З14.

## Нефункциональные требования

Целевые значения — предложение аналитика; они подтверждаются после ответов на З1, З12 и П15.

| Показатель | Цель | Примечание |
| --- | --- | --- |
| Передача заказа в WMS | 95% за 2 минуты, 99,9% за 15 минут | При доступной WMS |
| Статус в магазине после события WMS | 95% за 1 минуту при вебхуках | При опросе — до 5 минут |
| Остаток на сайте после изменения на складе | До 5 минут | Переход через 0 — без пакетирования |

| Потеря сообщений | 0 | Outbox, DLQ, ежедневная сверка |
| Хранение журнала обмена | 30 дней, персональные данные маскируются | См. «Безопасность» |
| Расширяемость | Новый склад или партнёр — новым адаптером без изменения магазина | Канонические сообщения |

## Тестирование, приёмка и запуск

Интеграция принимается, когда все сценарии ниже пройдены на тестовом стенде партнёра, а пилот на реальных заказах прошёл без потерь и ручных исправлений.

### Сценарии приёмки

- [ ] Предоплаченный заказ доходит до статуса «Доставлен» с трек-номером
- [ ] Заказ с оплатой при получении передаётся только после подтверждения оператором
- [ ] Заказ с несинхронизированным SKU получает «Проблему» и не уходит в WMS
- [ ] Повторная отправка того же заказа не создаёт дубль в WMS
- [ ] Повторный вебхук с тем же `event_id` не меняет данные второй раз
- [ ] Событие со старым статусом после нового не откатывает статус
- [ ] Отмена до передачи, отмена после передачи, отказ WMS в отмене
- [ ] Недостача при сборке переводит заказ в «Проблему» и создаёт задачу
- [ ] WMS недоступна 30 минут: заказы копятся и уходят после восстановления без потерь
- [ ] Неверная подпись вебхука — ответ 401, событие не обрабатывается
- [ ] Остаток 0 снимает товар с продажи в пределах 5 минут
- [ ] Ежедневная сверка находит и исправляет искусственно внесённое расхождение
- [ ] Принятый возврат возвращает годный товар в продажу и создаёт задачу на возврат денег
- [ ] Нагрузочный тест: 10-кратный средний поток заказов за час

### Запуск

1. Первичная выгрузка справочника товаров и сверка штрихкодов с партнёром.
2. Первичная загрузка остатков из WMS и сверка с фактом склада.
3. Перенос открытых заказов: решить, какие передаются через интеграцию, а какие доводятся вручную.
4. Пилот: интеграция включается флагом для части заказов (например, одной службы доставки) на 3–5 дней.
5. Полное включение после пилота без критичных дефектов.
6. План отката: флаг выключает отправку, заказы копятся в outbox и передаются вручную или после исправления.
