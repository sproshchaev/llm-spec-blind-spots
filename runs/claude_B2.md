## 4. Цели, границы и участники

Интеграция без ручного ввода передаёт заказы магазина в WMS партнёра и возвращает в магазин статусы отгрузки, трек-номера и остатки.

**Цели.** Ни один заказ не теряется и не дублируется на складе. Статус заказа в магазине отражает факт на складе с задержкой не больше целевой (раздел 9). Витрина не продаёт товар, которого нет на складе.

**В объёме первой фазы:** синхронизация справочника товаров (магазин → WMS), передача заказов, отмена, приём статусов и трек-номеров, приём остатков, ежедневные сверки, ручные операции для поддержки.

**Вне объёма:** возвраты, приёмка поставок, статусы доставки от курьерских служб, расчёты с партнёром за услуги.

| Система | Роль в интеграции | Мастер данных | Владелец |
| --- | --- | --- | --- |
| Платформа магазина | Источник заказов и карточек товаров, потребитель статусов и остатков | Заказы, товары, цены | Заказчик |
| Интеграционный сервис (новый) | Принимает события, преобразует форматы, гарантирует доставку, ведёт журнал и сверки | Соответствие идентификаторов, состояние обмена | Команда заказчика |
| WMS партнёра | Принимает заказы, собирает и отгружает, сообщает статусы и остатки | Физические остатки, статусы сборки, трек-номера | Логистический партнёр |

| Термин | Значение |
| --- | --- |
| SKU | Артикул товара магазина; единый ключ товара в обеих системах |
| Доступный остаток | Количество, которое WMS может отдать под новые заказы: физический остаток минус резервы, брак и карантин |
| Идемпотентность | Повтор одного и того же запроса не создаёт второго заказа и не меняет результат |
| Outbox | Таблица исходящих событий в БД магазина, записываемая в одной транзакции с изменением заказа |
| Время отсечки | Час, до которого принятый заказ склад отгружает в тот же день |
| Сверка | Плановое сравнение заказов и остатков в обеих системах с исправлением расхождений |

## 5. Архитектура

Магазин и WMS не вызывают друг друга напрямую: между ними работает отдельный интеграционный сервис со своей базой состояния и очередью. Так сбой WMS не блокирует оформление заказов, а адаптер под конкретную WMS можно заменить, не трогая ядро магазина.

Сервис складывает события магазина и вебхуки WMS в свою очередь, поэтому сбой одной стороны не блокирует другую.

| Решение | Обоснование |
| --- | --- |
| Магазин публикует события через outbox: запись события в той же транзакции, что и смена статуса заказа | Событие не теряется при сбое между сохранением заказа и отправкой |
| Сервис отправляет запросы в WMS асинхронно, через очередь с повторами | Временная недоступность WMS не приводит к потере заказов |
| Изменения от WMS приходят вебхуками; дополнительно раз в 5 минут сервис опрашивает изменения по метке времени | Опрос страхует от потерянных вебхуков; если вебхуков нет (П-04), опрос становится основным каналом |
| Обновления в магазин сервис пишет через внутренний API магазина, а не напрямую в его БД | Бизнес-правила магазина (уведомления, история заказа) срабатывают штатно |
| Адаптер WMS — отдельный модуль с внутренней канонической моделью заказа | Переход на файловый обмен или другую WMS меняет только адаптер |

Компоненты сервиса: приёмник событий магазина, адаптер WMS (исходящие вызовы), приёмник вебхуков, планировщик опроса и сверок, база состояния (соответствие идентификаторов, журнал событий, очередь повторов), служебный API для ручных операций.

## 6. Потоки данных

Пять потоков: справочник товаров и заказы идут из магазина в WMS, статусы и остатки — обратно; отмена — двусторонний обмен с подтверждением.

| Поток | Направление | Триггер | Канал |
| --- | --- | --- | --- |
| 6.1 Справочник товаров | Магазин → WMS | Создание или изменение складских атрибутов товара | Событие → API WMS |
| 6.2 Передача заказа | Магазин → WMS | Заказ готов к сборке (З-01) | Событие → API WMS |
| 6.3 Отмена и изменение | Магазин → WMS → магазин | Отмена или изменение заказа в магазине | Событие → API WMS, ответ или событие |
| 6.4 Статусы отгрузки | WMS → магазин | Смена статуса заказа в WMS | Вебхук + опрос |
| 6.5 Остатки | WMS → магазин | Изменение остатка в WMS; полная выгрузка раз в сутки | Вебхук или опрос + ночной снимок |

### 6.1 Справочник товаров

1. Магазин публикует событие `product.upserted` при создании товара или изменении складских атрибутов: название, штрихкоды, вес, габариты, признаки учёта.
2. Сервис преобразует карточку в формат WMS и вызывает создание или обновление по SKU.
3. Сервис сохраняет результат в таблице `sku_sync`: статус, время, текст ошибки.

Заказ с SKU, который ещё не принят WMS, не отправляется: он получает состояние «Ожидает справочника», сервис ставит товар на повторную синхронизацию и шлёт алерт. Перед запуском весь активный каталог выгружается в WMS пакетно.

### 6.2 Передача заказа

1. При переходе заказа в статус готовности к сборке магазин в той же транзакции пишет событие `order.ready_for_fulfillment` в outbox.
2. Сервис забирает событие и проверяет заказ: все SKU синхронизированы, обязательные поля заполнены, адрес и телефон в допустимом формате.
3. Сервис преобразует заказ в формат WMS (раздел 7.1). Ключ идемпотентности — номер заказа магазина плюс номер версии.
4. Сервис отправляет заказ в WMS:
   - успех — сохраняет идентификатор заказа в WMS, состояние «Передан на склад»;
   - ответ «заказ уже существует» — считает успехом и получает идентификатор из ответа или отдельным запросом;
   - ошибка валидации — состояние «Ошибка передачи», задача оператору, без повторов;
   - таймаут, 5xx, 429 — повтор по графику из раздела 8.
5. Сервис обновляет статус заказа в магазине через внутренний API.

### 6.3 Отмена и изменение

1. Отмена в магазине публикует событие `order.cancel_requested`. Если заказ ещё не передан в WMS, сервис просто снимает его с отправки.
2. Иначе сервис вызывает отмену в WMS.
3. WMS подтвердил — заказ в магазине получает статус «Отменён», резерв снимается.
4. WMS отказал (заказ уже собран или отгружен) — заказ в магазине получает признак «Отмена отклонена складом», оператор получает задачу: перехватить посылку или оформить возврат.

Изменение состава или адреса: если API WMS поддерживает правку заказа (П-08), сервис отправляет обновление. Если нет — отмена и повторное создание с новой версией (`{номер}-v2`), но только пока заказ не взят в сборку.

### 6.4 Статусы отгрузки

1. WMS вызывает вебхук сервиса; сервис проверяет подпись и сразу отвечает 200, обработка идёт асинхронно.
2. Сервис отбрасывает дубли по идентификатору события и находит заказ по внешнему номеру.
3. Сервис переводит статус WMS в статус магазина (раздел 7.3). Статус старше уже применённого — по метке времени или порядку статусов — игнорируется и пишется в журнал.
4. При статусе «Отгружен» сервис сохраняет трек-номер и службу доставки.
5. При частичной сборке WMS передаёт фактическое количество по строкам; разница обрабатывается по правилу из ответа на З-05 и уходит оператору.
6. Сервис обновляет заказ в магазине; уведомления клиенту отправляет магазин.

### 6.5 Остатки

Остатки приходят двумя путями: изменения — вебхуком или опросом раз в 5 минут; полный снимок по всем SKU — каждую ночь. Сервис всегда записывает в магазин абсолютное значение, а не прибавку: потерянное сообщение исправит следующее. Снимок применяется, только если он новее последнего применённого по этому SKU.

Доступный для продажи остаток в магазине считается так:

```latex
Остаток_{витрина} = Доступно_{WMS} - Резерв_{не\ переданные} - Страховой\ запас
```

Резерв по непереданным — это позиции заказов, уже оформленных в магазине, но ещё не принятых WMS: склад о них не знает и не вычел их из доступного. Страховой запас задаётся настройкой на SKU или на весь каталог (З-11).

Ниже — каноническая модель сервиса. Имена полей WMS условные и заменяются по документации партнёра (П-05, П-07); источники в магазине уточняет команда платформы. Все даты передаются в ISO 8601 с часовым поясом, хранятся в UTC.

## 8. Ошибки, повторы, идемпотентность и сверки

Технические сбои сервис повторяет сам, бизнес-ошибки сразу отдаёт оператору; ежедневная сверка ловит всё, что прошло мимо этих механизмов.

### 8.1 Классы ошибок

| Класс | Примеры | Действие сервиса |
| --- | --- | --- |
| Временная техническая | Таймаут, обрыв соединения, HTTP 5xx | Повтор по графику 8.2 |
| Превышение лимита | HTTP 429 | Повтор после паузы из заголовка Retry-After, иначе по графику |
| Бизнес-ошибка | HTTP 4xx с кодом валидации, неизвестный SKU, неверный адрес | Без повторов; состояние ошибки, задача оператору с текстом ошибки WMS |
| Ошибка аутентификации | HTTP 401, 403 | Остановка отправки, критический алерт |
| Дубль входящего события | Повторный вебхук с тем же event\_id | Ответ 200, повторно не обрабатывается |
| Нарушение порядка | Статус PICKING после SHIPPED | Игнорируется, запись в журнал |

### 8.2 График повторов

Задержки: 30 секунд, 2, 10, 30 минут, затем раз в час до 24 часов с момента первой попытки, к каждой задержке добавляется случайный разброс до 20%. После 24 часов задание переходит в очередь неисправимых ошибок, оператор получает алерт. Пока WMS недоступна, задания копятся в очереди и отправляются по порядку после восстановления.

### 8.3 Идемпотентность

- Исходящие: каждый вызов создания заказа несёт ключ «номер заказа + версия». Если WMS отклоняет дубль по внешнему номеру, ответ «уже существует» считается успехом. Если WMS такой защиты не даёт (П-05), сервис перед повторной отправкой после таймаута проверяет, нет ли заказа в WMS.
- Входящие: событие записывается в `inbox_event` с уникальным event\_id до обработки. Если WMS не передаёт идентификатор события, ключом служит связка «заказ + статус + время статуса».
- Остатки и статусы применяются как абсолютные значения, поэтому повтор не искажает данные.

### 8.4 Сверки

| Сверка | Когда | Что сравнивается | Действие при расхождении |
| --- | --- | --- | --- |
| Зависшие заказы | Каждые 15 минут | Заказы в состоянии «Ожидает отправки» дольше 30 минут | Алерт |
| Статусы заказов | Ежедневно, 06:00 по времени склада | Все незавершённые заказы магазина и их статусы в WMS | Статус магазина обновляется по WMS; заказы, которых нет в WMS, уходят в отчёт оператору |
| Остатки | Ежедневно после ночного снимка | Остаток каждого SKU в магазине и в WMS | Остаток перезаписывается; SKU с расхождением больше 5 единиц или 10% — в отчёт |
| Справочник | Еженедельно | Активные SKU магазина и товары в WMS | Недостающие SKU отправляются повторно |

### 8.5 Ручные операции

Служебный API (и простой экран в админке магазина): повторить отправку заказа, принудительно запросить статус заказа в WMS, повторно синхронизировать SKU, просмотреть журнал обмена по номеру заказа, перезапустить задания из очереди неисправимых ошибок. Каждая ручная операция пишется в журнал с именем пользователя.

## 9. Безопасность, мониторинг и НФТ

Целевые значения ниже — стартовые; часть из них подтверждается ответами З-10, З-13 и П-12.

### 9.1 Нефункциональные требования

| Требование | Целевое значение | Зависит от |
| --- | --- | --- |
| Задержка «заказ готов → принят WMS» | До 1 минуты для 95% заказов при доступной WMS | П-13 |
| Задержка «статус в WMS → статус в магазине» | До 5 минут | П-04 |
| Актуальность остатков на витрине | До 15 минут | З-10, П-10 |
| Пропускная способность | Трёхкратный пиковый поток заказов в час | З-13 |
| Недоступность WMS без потери данных | До 24 часов | — |
| Доступность интеграционного сервиса | 99,5% в месяц | — |
| Хранение журнала обмена | 90 дней | З-17 |

### 9.2 Безопасность

- Все соединения по TLS 1.2 и выше; ключи и секреты — в хранилище секретов, не в коде и не в конфигурационных файлах.
- Вебхуки WMS принимаются только с подписью HMAC (или другим механизмом из П-02) и с белого списка IP; неверная подпись — ответ 401 и запись в журнал.
- Партнёру передаётся минимум персональных данных, нужный для доставки (З-17).
- В журналах телефон, email и адрес маскируются; полный payload с ПДн хранится не дольше срока из 9.1.
- Служебный API доступен только из внутренней сети и по ролям.

### 9.3 Мониторинг и алерты

Каждый обмен пишется в журнал с корреляционным идентификатором, равным номеру заказа магазина или SKU.

| Алерт | Условие | Получатель |
| --- | --- | --- |
| WMS недоступна | 5 подряд неудачных вызовов или нет успешных вызовов 10 минут | Дежурный разработчик |
| Ошибка аутентификации | Любой ответ 401 или 403 от WMS | Дежурный разработчик |
| Заказ не передан | Заказ ждёт отправки дольше 30 минут | Оператор заказов |
| Бизнес-ошибка передачи | Любая | Оператор заказов |
| Очередь неисправимых ошибок | Не пуста | Дежурный разработчик |
| Остатки устарели | Нет успешного обновления остатков 30 минут | Дежурный разработчик |
| Нет статусов | Ни одного вебхука 2 часа в рабочее время склада | Дежурный разработчик |

Дашборд: заказов передано и с ошибкой за сутки, возраст самого старого непереданного заказа, длина очередей, задержка статусов (p50, p95), время последнего обновления остатков.

## 10. Тестирование, приёмка и внедрение

Интеграция принимается после прохождения всех сценариев в тестовой среде партнёра и пилота без потерянных заказов.

### 10.1 Сценарии интеграционного тестирования

| № | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| T-01 | Заказ проходит путь от оформления до отгрузки | Статусы в магазине сменяются по 7.3, трек-номер сохранён, клиент получил уведомления |
| T-02 | Заказ отправлен повторно после таймаута | В WMS один заказ, в магазине один идентификатор WMS |
| T-03 | В заказе SKU, не заведённый в WMS | Заказ «Ожидает справочника», SKU синхронизирован, заказ ушёл автоматически |
| T-04 | Ошибка валидации (некорректный адрес) | «Ошибка передачи», задача оператору, повтор после исправления успешен |
| T-05 | WMS недоступна 1 час | Заказы копятся в очереди, после восстановления переданы все и по порядку |
| T-06 | Отмена до начала сборки | Заказ отменён в WMS и в магазине, резерв снят |
| T-07 | Отмена после отгрузки | Признак «Отмена отклонена складом», задача оператору |
| T-08 | Частичная сборка | Фактическое количество по строкам сохранено, сработало правило З-05 |
| T-09 | Статусы приходят не по порядку | Устаревший статус проигнорирован, финальный не откатился |
| T-10 | Один вебхук приходит дважды | Обработан один раз |
| T-11 | Вебхук с неверной подписью | Ответ 401, данные не изменились |
| T-12 | Изменение остатка и ночной снимок | Витрина показывает значение по формуле 6.5 в пределах 15 минут |
| T-13 | Нагрузка: трёхкратный пиковый поток | Задержки в пределах 9.1, без ошибок |
| T-14 | Ежедневная сверка с намеренно внесённым расхождением | Расхождение исправлено и попало в отчёт |

### 10.2 Критерии приёмки

- Сценарии T-01…T-14 пройдены в тестовой среде, протокол подписан заказчиком и партнёром.
- Пилот на продуктиве: ноль потерянных и задублированных заказов, все расхождения сверок объяснены.
- Алерты и дашборд работают, регламент разбора ошибок согласован (З-15, П-14).

### 10.3 План внедрения

1. Получить ответы на вопросы разделов 2–3, документацию API и доступ к тестовой среде; выпустить спецификацию v1.0.
2. Разработать сервис: адаптер WMS, outbox в магазине, приём вебхуков, сверки, служебный API.
3. Выгрузить каталог в тестовую WMS и пройти сценарии 10.1.
4. Выгрузить продуктивный каталог; перенести в интеграцию заказы, которые уже на складе (З-14).
5. Пилот: часть заказов (например, один способ доставки) идёт через интеграцию, оператор ежедневно сверяет результаты вручную.
6. Перевести весь поток заказов; две недели усиленной поддержки.
7. Вторая фаза: возвраты и приёмка поставок (З-16, П-17).
